Status: proposed design for #573. Ordered model fallback, provider/account failover and bounded rate-limit retry already exist. This proposal uses fresh observed quota evidence to select among those routes and waits. [Provider models](/reference/provider/model)

## Decision

| Option | Consequence |
| --- | --- |
| Always wait for the preferred route | Can block work when evidence is missing or stale. |
| Always skip any exhausted route | Ignores a short known reset and a user's preference to wait. |
| Honor an opt-in, evidence-based bounded policy | Preserves current order by default and makes waiting and returning explicit. Selected. |

## Evidence and selection

The policy defaults to disabled and uses the existing candidate order when disabled. For an enabled policy, record provider/account/model scope, observed time, budget kind, remaining capacity when known and reset time when supplied. Evidence must come from a normalized provider response or a verified provider quota feed for exactly that authorized scope. Keep expiry no longer than 60 seconds after observation and before any unverified authorization change. A reset timestamp is eligibility to retry, not proof of capacity. Local usage accounting alone does not establish remote quota. Unknown, expired and unrelated evidence never reserves a wait.

The user chooses `fallback_first` or `wait_if_short` and a maximum single wait from 0 to 30 seconds. An exhausted route requires fresh evidence establishing a reset in the future. With `fallback_first`, follow existing order to an eligible route immediately. With `wait_if_short`, wait only if reset fits the configured maximum, existing retry/backoff cap, remaining effective deadline and request budget. If no eligible alternate exists, one allowed bounded wait may be used only with fresh evidence and consent. Sleep on the existing cancellable retry path. After waking, re-read state and allow one normal, budgeted attempt or use an eligible fallback. A stale or missing reset follows normal bounded retry/fallback rules. Do not extend a turn deadline or create a separate retry allowance. Report reason, scope label and wait duration without tokens or raw headers.

Return policy is `next_turn` or `session_sticky`, chosen when enabling the feature. `next_turn` reconsiders the preferred route at the next user turn if it is eligible. `session_sticky` stays on the new eligible route until explicit user switch or next required failover. Neither policy switches a stream mid-response. Reuse existing replay eligibility and authorization rules. A completed request or one whose outcome is ambiguous cannot be replayed by this policy.

## Implementation boundaries

1. In `crates/config-types/src/model_roles.rs`, define default-off wait and return settings. Keep the configured route order stable.
2. Under `crates/base/src/provider/`, normalize scoped evidence and freshness from already authorized provider traffic. Preserve existing auth and raw header redaction.
3. In `crates/app-core/src/agent/turn_failover.rs`, evaluate eligible alternatives, consume the existing retry budget and cancel the same wait on turn cancellation. Add controlled-clock receipts and cross-route fixture tests in Actions.

## Verification

Run `cargo test --locked -p horon-agent-app-core --lib`. With time 100 s, a preferred route exhausted until 108 s and an eligible second route, `fallback_first` selects the second immediately and `wait_if_short` with a 10-second cap waits 8 seconds. A 5-second cap selects the alternate. At time 103 s, cancellation ends the wait with zero redispatches. Expired, unknown or wrong-scope evidence causes no quota-specific wait. Verify that a subsequent turn honors each return policy, disabled mode preserves candidate order, and a completed request is never sent twice.
