This document covers the credential setup and the request and event surfaces of the harness API that desktop and SDK clients use over a local socket: a Unix socket, or a named pipe on Windows. Both mechanisms carry the same frames. A client that finds nothing listening at the socket path starts `horon-agent api-bridge` itself and waits on that path, so the bridge is a subcommand of the agent binary on every platform the SDK supports.

A client may read and write at the same time: the SDK client parks one thread in a read for the next frame while another writes a request, and the Windows pipe is opened for overlapped I/O so the pending read never holds the write behind it.

## Credential setup

This build has no interactive login flow. The SDK exposes two things about credentials.

- `HoronAgentClient::set_api_key(provider, key)` (TypeScript `setApiKey`) writes the key into horon-agent's owner-only credential store (a `SetApiKey` request with a `credential_updated` response) and re-reads the provider credentials. The key never appears in a response or a log.
- `notify_auth_changed(provider)` (TypeScript `notifyAuthChanged`) is the notice to re-read the credential files after the user logged in to OAuth with another tool. It sends no credentials itself, and the bridge advertises this through `auth_changed_notification`.

The SDK neither issues nor refreshes OAuth tokens. The launch option `inherit_logins` (on by default) links the user's existing CLI credential files into the instance, and model requests use those files as they are (`crates/agent-sdk/src/launch.rs`). Model calls go directly to the configured `[providers.<name>]` endpoint over the wire its `type` selects (`openai-compatible`, `openai-responses`, `anthropic-compatible`, or `gemini-compatible`), so this build has no model runtime that authenticates with OAuth. The `openai-oauth:` prefix still exists, but with that runtime gone it fails before the call (`docs/provider/MODEL.md`).

## Serving the API beyond the local socket

The default endpoint stays local: a Unix socket, a named pipe on Windows, or one stdio connection. A bridge can additionally serve the same frames on TCP, which is how a TLS-terminating proxy, an SSH forward or another machine reaches it. The local socket keeps its handshake byte for byte, so existing clients are unaffected.

| Switch | Where | Meaning |
| --- | --- | --- |
| `--api-bind IP:PORT` | `horon-agent api-bridge` | Serve the API on that TCP address beside the local socket |
| `HORON_AGENT_API_BIND` | environment | The same address, for a container entrypoint or a supervisor |
| `[harness_api] bind` | `config.toml` | The same address, for an installation that always exposes one |
| `--api-insecure-behind-proxy` | `horon-agent api-bridge` | Acknowledge that a TLS-terminating proxy fronts the address |
| `HORON_AGENT_API_INSECURE_BEHIND_PROXY` | environment | The same acknowledgement, `1` or `true` |
| `[harness_api] insecure_behind_proxy` | `config.toml` | The same acknowledgement |

The flag wins over the environment, and both win over the file. A bind value is a literal `IP:PORT` such as `127.0.0.1:7946` or `[::1]:7946`; a host name is refused, because resolving one at bind time must not decide whether the listener is loopback.

Two rules decide whether an address is allowed.

- **Every TCP connection authenticates.** Its first line must be `Authorization: Bearer <token>`, and the ordinary `hello` and every later frame follow unchanged. A missing, malformed, oversized (over 1 KiB), late (over 10 seconds), wrong or revoked token closes the connection before the daemon is dialled and before any request is read, and the bridge writes nothing back.
- **A non-loopback address also needs the proxy acknowledgement.** Built-in TLS is not implemented, so a non-loopback bind refuses to start unless the operator confirms that TLS terminates in front of it and at least one credential exists. A loopback TCP bind needs the credential but not the acknowledgement.

A bridge started with `--api-bind` is not terminal-owned: it does not exit when its parent process ends or when it has been idle, because an exposed endpoint has no terminal to belong to. Stop it with its supervisor, `docker stop`, or SIGTERM.

The bind value is parsed as a literal address, never resolved. Only `127.0.0.0/8` and `::1` are loopback; `0.0.0.0`, `[::]` and any other literal, including a private IPv6 address such as a Fly 6PN `fdaa::/16` one, are non-loopback and need both the credential and the proxy acknowledgement. A dual-stack listener binds `[::]:PORT`; a platform that routes to the process over IPv4 needs `0.0.0.0:PORT` instead. A host name such as `localhost:7946` is refused so that name resolution cannot decide which rule applies.

### Two network paths, two different guarantees

A listener on a network address is reached one of two ways, and they are not equivalent.

| Path | TLS | Who can reach it | What it proves |
| --- | --- | --- | --- |
| Public port through the platform proxy | Terminated by the proxy, which forwards plaintext to the process over the provider's private mesh | Anyone the proxy routes; the port is public unless the app has no public IP | The bearer token alone |
| Provider private network | None, by design | Anything on the organization's private network, by internal address | The bearer token alone |

Neither path authenticates a *user*: the private network keeps other organizations out, but every process on it is equally trusted, and a public port is public. That is why every TCP connection presents the token on both paths, and why the proxy acknowledgement exists only to state where TLS ends — never to stand in for authentication. The listener trusts no forwarded header, so `Fly-Client-IP` or any other proxy header never affects who is accepted.

On Fly.io, which is the hosting target for `docs/architecture/HOSTING.md`: the public path is a `services` entry in `fly.toml` (or the Machine config) whose `internal_port` matches `--api-bind`, with Fly Proxy terminating TLS on port 443 and forwarding plaintext to the process over the WireGuard mesh — so that path passes `--api-insecure-behind-proxy`. The private path is the organization's 6PN: a service is reachable there when it binds the IPv6 wildcard (`[::]:PORT`) or `fly-local-6pn`, and needs no `services` entry and no app IP. 6PN addresses are IPv6 literals in an `fdaa::/16` ULA, so `[fdaa:…]:PORT` and `[::]:PORT` are both non-loopback binds that need the proxy acknowledgement and a credential. A Fly Machine that is stopped or suspended has no running process, so its listener, its sockets and any in-memory session are gone; the credential file stays on the volume and keeps working after the next start. The listener therefore does not exit on idleness or when the starting process goes away (see above), and the control plane's autostop policy is what ends it. Those platform details are documented by Fly.io (`docs.fly.io/networking/tls-termination`, `docs.fly.io/networking/app-services`); this repository implements no Fly API call, no proxy-header handling and no autostop.

### Issuing, rotating and revoking credentials

| Command | Effect |
| --- | --- |
| `horon-agent api-credentials issue --label NAME` | Create one credential and print its token once |
| `horon-agent api-credentials rotate ID` | Replace one credential's token and print the new token once |
| `horon-agent api-credentials revoke ID` | Delete one credential; the next connection with its token is refused |
| `horon-agent api-credentials list` | Print id, label and timestamps, never a token |

The store is `$HORON_HOME/harness-api/credentials.json`, mode `0600` inside a `0700` directory, and it holds only `sha256:<hex>` digests: a token exists in the clear only in the output of `issue` and `rotate`. The bridge re-reads the file for every connection, so revoke and rotate apply without restarting it. A store that became a symlink, changed owner or lost its owner-only mode refuses every authentication instead of trusting it. In a per-user container the file lives in that tenant's `HORON_HOME`, so credentials are per user by construction and `list` names the tenant as their namespace.

A client on another machine supplies its own transport: terminate TLS at the proxy in front, forward plaintext to the `--api-bind` address, and send the authorization line before `hello`. Neither SDK has a built-in TCP transport and this build adds none, so SSH forwarding to the local socket or the proxy in front of `--api-bind` is the supported path. Client certificates at that proxy are the supported mutual-authentication path; built-in mTLS is a deliberate follow-up, not a silently dropped feature.

## Session goals

Send `runtime_command` with the command `goal` and arguments `["1200", "Ship a fix"]` to attach a goal to the selected session. The first argument is a positive token ceiling. The response contains the saved goal and a display message. The command leaves an existing active goal in place and returns an error if another is requested.

## Durable runtime API (protocol 1.14)

The major version stays at `1` and the minor version moved from 13 to 14. Every surface below is additive. The byte representation of existing requests and the shape of their responses are unchanged, and a client that sends none of the new requests behaves exactly as before.

The bridge advertises four capabilities. A client checks them before sending anything.

| Capability | Surface it gates |
| --- | --- |
| `durable_runtime_v1` | `get_runtime_state`, `apply_control`, `get_control_receipt` |
| `monitor_v1` | None. Monitors start and stop through existing tool calls, so this is a marker telling a client how to read results |
| `snapshot_marker_v1` | `get_snapshot` and the `snapshot_marker` event |
| `ask_receipts_v1` | The optional `answer_id` of `ask_response` |

A request sent without the capability is rejected with a structured `unsupported` error that names the missing capability. It is not treated as success, and it is not a version error. Both SDKs provide methods with the same names (`get_runtime_state`/`getRuntimeState`, `apply_control`/`applyControl`, `get_control_receipt`/`getControlReceipt`, `get_snapshot`/`getSnapshot`, `respond_to_ask_with_id`/`respondToAskWithId`) and reject the request before writing it to the socket when the capability is absent. That is the point where an old server can no longer receive an unknown request and mishandle it.

### State summary

`get_runtime_state` returns a **summary** of runs, queue, receipts and monitors from the session's durable journal. Accepted input bodies, command arguments and command environment variables never appear here. A status panel needs counts, phases and causes, not the sentences sitting in the queue.

| Field | Meaning |
| --- | --- |
| `journal` | Whether the journal exists, its generation, last seq, bytes, record count and whether it is read-only |
| `runs` | Runs that have not finished: `run_id`, `started_at`, optional `input_id` |
| `queue` | Live input count, inputs whose result is not settled, held bytes |
| `receipts` | Completed and cancelled input receipts, newest first: `input_id`, `phase`, `seq` |
| `monitors` | Monitor id, kind, whether it stopped, a summary sentence of the last checkpoint |
| `pending_wakes` | Number of wakes not yet delivered |
| `pending_controls` | Number of controls that have not finished |
| `last_stop` | Cause and time the last run ended |

### Control and receipts

`apply_control` applies a control action under a caller-chosen `operation_id`. Sending the same id again returns the recorded receipt and does not apply the action twice. `get_control_receipt` reads that record. `outcome` is one of `applying`, `terminal`, `replay`, `conflict`, `unknown` and `indeterminate`. `indeterminate` means the action started but its terminal record could not be written, so the result is unknowable, and it is never retried automatically.

### Snapshots and markers

`get_snapshot` returns state plus a bounded history tail at one consistent point in time. Just before the response a `snapshot_marker` event arrives on the same connection first, and both frames carry the same `marker_id`. Every live event that arrives afterwards is newer than that snapshot. The marker is a stream event without `reply_to`, so a client classifies the boundary by that rule instead of guessing from arrival order. `generation` changes on every restart and promises nothing about replaying past `seq` values.

`get_snapshot` takes `tail` (default 20, maximum 100) and `max_bytes` (default 262,144, maximum 1 MiB), and `truncated` becomes true when the budget cuts the tail.

### Answer receipts

`ask_response` gained an optional `answer_id`. Sending the same `answer_id` with the same answer for the same `ask_id` counts as one answer, so a retry after a lost response does not resolve the question twice. A different `answer_id` for the same question is a conflict. The existing path that sends no `answer_id` works as before and needs no capability negotiation.

### New events

Four events were added: `runtime_state`, `control_receipt`, `snapshot_marker` and `snapshot`. All are gated by a capability; the server does not send them to a connection that did not negotiate it, and the SDK discards them after receiving them. Byte-level behaviour of existing connections is unchanged.

### Where the answers come from

All four requests are served. The daemon advertises `durable_runtime_api` in its `pong` (`crates/app-core/src/server/session_connections.rs`) and owns the session, its cancel signals and the control ledger, so the bridge only translates a request into the daemon's own frame and translates the reply back (`crates/harness-api-server/src/translate.rs`); the daemon dispatches them in `crates/app-core/src/server/client_lifecycle.rs` and builds the snapshot from the session's observation owner (`crates/app-core/src/server/runtime_state_api.rs`).

`unsupported` therefore means **this daemon is older**, not that the surface is unimplemented. The bridge returns it, naming `durable_runtime_v1`, only when the daemon it dialled did not advertise `durable_runtime_api`: an older daemon answers an unknown request with an error frame carrying no id, so forwarding would leave the client waiting out its own timeout. From the client's side that is the same "this server does not offer it" answer as any other missing capability, so no branching changes.

## Package catalog control (protocol 1.26)

The bridge advertises `package_control_v1` when the daemon's `pong` advertises
`package_control`. A `package_control` request carries an `operation_id` and an
`operation`. A successful response carries the published generation and its
catalog, including each package's scope and any removal records. The daemon
applies catalog changes through the same store lock used by the standalone CLI.
Clients can continue to use the existing protocol with an older daemon. A
package control request requires the advertised capability.

The daemon checks for complete inbox folders at startup and during filesystem
reconciliation. A status request reads the published snapshot. Subscribers
receive the latest complete snapshot even if they miss intermediate updates.
When a mutation returns a transport error after sending the request, inspect
the published state before submitting it again.

## Package commands (protocol 1.27)

The harness API keeps major version 1 and moved from minor version 26 to 27.
Everything here is additive: a client that never lists a package command reads
the same frames it did before.

The bridge advertises `package_commands_v1` only when the daemon reported
`runtime_commands`, because these two values ride that request instead of a
request of their own. A client checks the capability before sending, and the
three SDKs refuse the call in the process when it is absent, so an older server
never receives a value it cannot answer.

| Value | `args` | `data` in `runtime_command_result` |
| --- | --- | --- |
| `package_commands` | empty | `PackageCommandList`: the generation, and the commands sorted by name |
| `package_command` | `[package_id, command, …argument words]` | `PackageCommandOutcome`: the expansion or the child's answer |

One entry carries the typed name, the package that declares it, the declared
command name, the kind, one description line and the `argument_hint` the
resource declares when it declares one. `kind` is `template` for a Markdown
resource that expands into a user message and `executable` for a command the
package's child answers over the wire.

```json
{"v":1,"id":9,"req":"runtime_command","session_id":"s-1","command":"package_commands"}
{"v":1,"reply_to":9,"ev":"runtime_command_result","session_id":"s-1","command":"package_commands","data":{"generation":7,"commands":[{"name":"hello:greet","package_id":"hello","command":"greet","kind":"executable","description":"Report the arguments this executable command was called with."},{"name":"hello:review","package_id":"hello","command":"review","kind":"template","description":"Review a file","argument_hint":"<path>"}]},"message":"..."}
```

An outcome sets exactly one of `text` and `output`: a template sets `text`, the
message a client submits, and an executable command sets `output`, the child's
value rendered as text, beside `data`, the same value unrendered. `message` in
the result frame repeats whichever one is set, so a client that only prints the
message needs no new parsing.

Both values read the package generation the session captured at its turn
boundary. A listing names that generation, and a run refuses an entry whose
package left it before reading a file or starting a child; the error says the
entry is stale. Executable commands consult plan mode, the approval mode, the
session's disabled names and the `pre_tool` hook, and they do not consult the
tool allow-list, which names the tools a model may call rather than the commands
a user types. The policy name is `ext__<package id>__<command>`.

The three SDKs expose the pair as `list_package_commands` and
`run_package_command` in Rust and Python, and as `listPackageCommands` and
`runPackageCommand` in TypeScript. ACP v1 and v2 are unchanged: their
`available_commands_update` still carries the client's own `/model`, `/models`
and `/effort`, because a package command is a harness API surface, not an ACP
one.

## Handoff compaction

`compact` takes an optional `method`. Absent is the model summary a client has
always requested: the reply is `compacted` and means the request was accepted,
because the daemon summarizes at its next safe point.

`method: "handoff"` writes a generated handoff document as the boundary instead,
and the reply arrives after that write. It is the outcome, not an
acknowledgement.

Request:

```json
{"id": 4, "req": "compact", "session_id": "s-1", "method": "handoff"}
```

Response, the same `compacted` event with `handoff` attached:

```json
{"id": 4, "event": "compacted", "session_id": "s-1", "message": "Committed a handoff document covering the first 120 messages.",
 "handoff": {"outcome": "committed", "covered": 120}}
```

| `handoff.outcome` | Meaning |
| --- | --- |
| `committed` | The document became the boundary. `covered` is how many messages it covers; the recent-token tail stays verbatim |
| `nothing_to_cover` | Every message fits inside the recent-token budget, so no document was written |
| `provider_error` | The completion failed, or its document was refused (empty, or without a `Goal` heading). `detail` carries the provider's message or the refusal reason. The transcript is unchanged |
| `cancelled` | The generation was cancelled before it answered. The transcript is unchanged |

No capability gates this field: a server that predates it ignores an unknown
field on the request and answers without `handoff`, so a client that sends
`method` to an older daemon must treat a missing `handoff` as "not supported by
this server" rather than as `nothing_to_cover`. A value the server does not know
is refused as `invalid_request`.

The request itself has no cancel signal. One bounded completion decides it, so a
client that stops waiting leaves the generation running; it does not roll back a
boundary that is already committed.

## Rewind branch summary

`rewind` takes an optional `summarize`. Absent or `false` is the request a client
has always sent and the daemon behaves identically.

`summarize: true` asks the daemon to write a report on the branch the rewind
discards and append it to the kept branch as one hidden system reminder, so the
model sees why the abandoned attempt failed without the transcript carrying the
whole dead branch. The report covers what was tried, what failed and why, and
which facts the branch established.

The feature is off unless the daemon's `[compaction] rewind_summary` is on. The
allowance for the report comes from `[compaction] rewind_summary_tokens`; its
default 1500 is horon's own choice, and values are clamped to `1..=4096`, with
`0` meaning "use the default".

Request:

```json
{"id": 7, "req": "rewind", "session_id": "s-1", "message_index": 12, "summarize": true}
```

The rewind happens first and the report second, so a summary failure never leaves
the conversation where it was:

| What happened | Message history |
| --- | --- |
| Setting off | Rewound, no report appended |
| Report written | Rewound, one hidden `<system-reminder>` message appended after the stop point |
| Nothing to discard | Rewound, nothing appended |
| Completion failed | Rewound, nothing appended; the reason appears in `status_detail` on the `history` reply and in the daemon log |
| Completion cancelled | Rewound, nothing appended |

The appended report is not a visible transcript message and not a rewind target,
so a later `/rewind N` counts the same entries it counted before. `rewind_undo`
restores the head recorded before the rewind, which removes the report together
with everything else the rewind discarded.

No capability gates this field: a server that predates it ignores the unknown
field and answers with a plain rewind, so a client that sends `summarize` to an
older daemon gets the old behavior rather than an error.

## Tool argument repair (protocol 1.16)

A provider's JSON writer sometimes types a tool argument wrong: `"5000"` where a
number belongs, `1` where a boolean does. The dispatcher repairs those before the
tool runs, and the repair is now visible three ways. Everything here is
additive: a client that predates it sends the same requests and reads the same
events as before.

### Event: `tool_args_repaired`

Sent immediately before the call's `tool_done`, once per repaired call. A client
that does not know the event ignores it, and the call finishes either way.

```json
{"ev":"tool_args_repaired","session_id":"s-1","call_id":"call-9","name":"bash",
 "original_input":{"command":"ls","timeout":"5000"},"changes":["coerced `timeout` to a number"]}
```

`original_input` is the arguments exactly as the model sent them, and `changes`
is one line per repair, in the order the repairs were applied.

### Stored record

The stored tool result carries the same two values as `original_input` and
`arg_repairs`. Both are omitted when the call needed no repair, so every other
record keeps exactly the bytes it had before.

### Counter

`snapshot().tool_arg_repairs` counts repaired calls per tool, when
`HORON_AGENT_PERF_COUNTERS=1`.

## Degradation receipts (protocol 1.17)

horon-agent narrows the tool catalog before a request leaves when the
provider's schema dialect cannot express part of it. Each narrowing is now
recorded. Everything here is additive: a client that predates it sends the same
requests and reads the same events as before.

### Event: `degradation_receipts`

Sent after the assistant message of a streamed turn is stored, only when that
request lost something not already reported in this session. A client that does
not know the event ignores it.

```json
{"ev":"degradation_receipts","session_id":"s-1","message_id":"m-7",
 "receipts":[{"kind":"schema_keyword_dropped","tool":"bash","target":"uniqueItems"}]}
```

`kind` is one of `schema_keyword_dropped` (a keyword, or `format:<value>`, outside
the dialect), `strict_disabled` (the tool was sent with `strict: false`) and
`duplicate_tool_dropped` (a second definition of the same name was not sent).
Each distinct (kind, tool, target) is reported once per session, not once per
request; a daemon restart may report it once more.

### Stored record

The assistant message appended for that request carries the same receipts as
`degradations`, written in the same append. A message whose request lost nothing
omits the field and keeps exactly the bytes it had before.

### Rejected-then-retried requests

Prevention narrows the catalog against a declared allow-list, so a construct
outside it never reaches the provider. The allow-list cannot be complete,
though, and a provider that still rejects one would otherwise fail every turn
carrying that tool.

The direct Chat Completions path now recovers from that rejection inside the
same turn. A `4xx` whose body names a schema keyword or `format` is learned,
the tool catalog is rebuilt without it, and the request is sent once more; the
loss appears as an ordinary `schema_keyword_dropped` receipt on the retried
request, so a client sees the same `degradation_receipts` event it already
handles. Learning is bounded per construct, so a second rejection naming the
same thing is reported instead of retried.

Only a client error can teach the dialect anything. A `429`, `5xx` or `401/403`
is a transient or credential failure: recovery neither learns from it nor
retries it, so the shared failover classification sees the status it always did.
An error that names nothing strippable, such as #713's "schema must have a
`type` key", is reported on the first failure with a hint saying a retry cannot
help.

## Message delivery modes (protocol 1.18)

A message that arrives while a turn is running is held in the session's pending
queue and injected at the next delivery point. `[messages]` decides how many of
those each point carries and whether one stops the running tools. Everything here
is additive: a client that predates it sends the same requests and reads the same
events as before.

| Key | Values | Default | Meaning |
| --- | --- | --- | --- |
| `follow_up_mode` | `all`, `one-at-a-time` | `all` | Queued messages the first delivery point of a turn carries; those are left over from the previous turn |
| `steering_mode` | `all`, `one-at-a-time` | `all` | Queued messages each later delivery point of the same turn carries |
| `interrupt_mode` | `wait`, `immediate` | `wait` | Whether a queued message waits for the running tool call or stops the remaining ones |

Both defaults of `all` keep the behavior horon has always had. That deliberately
differs from omp, whose default is `one-at-a-time` for both queue modes: an
unconfigured daemon must not start splitting messages it used to deliver together.
`one-at-a-time` leaves the rest pending, in order, so each message gets its own
injection.

### Request: `get_message_modes`

```json
{"v":1,"id":7,"req":"get_message_modes","session_id":"s-1"}
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | Yes | Session the question is about |

### Response: `message_modes`

```json
{"v":1,"reply_to":7,"ev":"message_modes","session_id":"s-1",
 "modes":{"follow_up_mode":"all","steering_mode":"one-at-a-time","interrupt_mode":"wait"}}
```

The strings are the config spellings, so a client never maps an enum back to
text.

### Behaviour

The values are daemon configuration rather than session state. The bridge answers
the request itself in `crates/harness-api-server/src/message_modes.rs` without a
daemon round trip, and the answer does not depend on the named session existing:
a client reads the modes of the daemon it is talking to, before or without a
session.

No capability gates the pair. The request is additive, so a server that predates
it answers `unknown_request`; a client that gets that error treats the modes as
unknown rather than assuming the defaults. The SDKs expose the call as
`get_message_modes` (Rust, Python) and `getMessageModes` (TypeScript).

For a text-only tool attempt, `soft_interrupt_injected` carries `point: "native_tool_retry"` and an optional `notice` for display. The notice describes the upcoming retry. Interrupts without a display notice omit that field.

A daemon advertising `turn_retry_v1` checks `expected_run_id` on a `send_message` request that continues a failed turn. The check and the start share the same session lock. If another request has already continued or replaced the run, the daemon refuses it before adding any message.

## Tool verdict (protocol 1.19)

The harness API keeps major version 1 and moved from minor version 18 to 19.
Everything here is additive: a client that never looks at the new field reads
the same events it did before.

A tool call used to report only text plus an error flag, so a client that wanted
to know whether a call ran, ran in part, or was refused had to read the
sentence. The stored `tool_result` already carries a typed verdict; this version
puts the same value on the event that closes the call.

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `verdict` | string | No | What became of the call, when the daemon stored a verdict for it |

The values are the seven wire spellings the stored result uses.

| Value | Meaning |
| --- | --- |
| `ok` | The tool ran and its whole result was returned |
| `partial` | The tool ran, but only part of the work finished |
| `truncated` | The tool ran to the end; the returned text is a cut of the full text |
| `withheld` | The tool ran, and a refusal sentence was returned in place of its result |
| `rejected` | The call was refused before the tool ran |
| `failed` | The tool ran and returned an error |
| `interrupted` | The call was skipped or cut short by the user, a reload, or a cancellation |

The field is absent when no layer made a statement about the call. Most tools
say nothing about a call that simply succeeded, so the usual successful
`tool_done` carries no verdict; `ok` appears only where a tool states it. A call
that moved to the background carries none, and neither does a tool the provider
runs on its own side (a hosted search, for example), even when that tool reports
an error. A result the provider supplies for a tool call the model made is
`failed` when it comes with an error flag. An absent field leaves the frame
byte-identical to protocol 1.18, and a reader then tells success from failure by
`error`, exactly as before.

### Event: `tool_done`

```json
{"v":1,"ev":"tool_done","session_id":"s-1","call_id":"call-1","name":"bash",
 "output":"Error: command timed out","error":"Error: command timed out",
 "verdict":"failed"}
```

No capability gates the field. It rides on an event every client already reads,
so a client that predates it ignores the key; a client that wants the verdict
reads it and falls back to `error` when it is missing.

## Permanent session delete (protocol 1.20)

The harness API keeps major version 1 and moved from minor version 19 to 20.
The addition is one request, so a client that never sends it reads the same
frames it did before.

`archive_session` hides a session and keeps it loadable. This is the other
operation: the transcript and everything keyed by the session id are removed
from disk, and nothing restores them.

### Request: `delete_session`

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `req` | string | Yes | `"delete_session"` |
| `session_id` | string | Yes | The session to remove, as a full id or a unique prefix |
| `confirm` | boolean | No | The wire field behind the refusal; the bridge always sends `true` |

```json
{"v":1,"id":12,"req":"delete_session","session_id":"s-1"}
```

The reply is `{"v":1,"reply_to":12,"ev":"ok"}`.

### Behaviour

- A session a turn is running for, one another process is streaming, or one
  still attached to a client is refused with an error, because deleting under a
  live writer would race that writer. Close or detach it first. An idle session
  the daemon holds between turns, including one kept for its reconnect grace
  after its client left, is not open: it is closed and deleted.
- `detach_session` releases this connection's attachment before it answers
  `ok`, so a delete sent right after a detach cannot find the connection still
  attached.
- A session this bridge connection is attached to is refused the same way, and
  the bridge says so before the round trip.
- An id that does not exist is `unknown_session`, the same answer as an
  unknown `attach_session`.
- A second delete of the same id succeeds, so repeating the call is safe.
- An archived session is deleted like any other. Archive and delete stay
  separate operations, and delete does not imply archive or the reverse.
- Process-wide state is not a session's and is never removed: managed skills,
  models, configuration, approvals, the usage database.

No capability gates the request. It is additive, so a server that predates it
answers `unknown_request`, which a client treats as "this build cannot delete"
rather than as a missing session. The SDKs expose it as `delete_session` (Rust, Python)
and `deleteSession` (TypeScript).

## Swarm chat surface removal (protocol 1.21)

The harness API keeps major version 1 and moved from minor version 20 to 21. This
entry is a **removal recorded, not a surface change**: the swarm chat primitives
that went away (`swarm` actions `share`, `share_append`, `read`, `channel`,
`list_channels`, `channel_members`, `subscribe_channel`, `unsubscribe_channel`,
and the `channel` argument of `swarm message`) lived on the internal daemon wire
(`horon-agent-protocol`) and in the `swarm` tool schema. None of them was ever
exposed as a harness API request, event, or field, so a client that spoke 1.20
sends and reads exactly the same frames.

The removal is recorded here because it changes what a session's transcript can
contain and what an old session replays:

- The wire requests `CommShare`, `CommRead`, `CommListChannels`,
  `CommChannelMembers`, `CommSubscribeChannel`, and `CommUnsubscribeChannel` are
  gone, as are the `CommContext` and `CommChannels` server events, the
  `SharedContext` notification type, the `channel` field on
  `NotificationType::Message`, `SwarmEventType::ContextUpdate`, and the
  `ContextEntry` and `SwarmChannelInfo` types.
- A stored session written before the removal keeps its `swarm` tool calls with
  their original names and arguments through load, projection, and render, so
  resuming it loses no transcript. Replay is covered by
  `session::tests::retired_swarm_actions`.
- A new call naming a removed action fails instead of degrading: the tool answers
  `Action '\<name>' was removed: the swarm shared-context store and topic channels
  are gone. Use action='message' (with to_session for a DM) ... and artifacts for
  durable data.` A `channel` argument on `message` is refused the same way. Both
  are covered by
  `tool::communicate::tests::input_format::retired_channel_and_shared_context_actions_are_rejected`.

### Migration

| Was | Now |
| --- | --- |
| `swarm {action:"dm"}` / `swarm {action:"message", to_session}` | unchanged |
| `swarm {action:"broadcast"}` / `swarm {action:"message"}` | unchanged; reaches the sender's spawned subtree |
| `swarm {action:"channel", channel, message}` | `swarm {action:"message", to_session}` for one agent, or without `to_session` for the subtree |
| `swarm {action:"share"\|"share_append"\|"read", key, value}` | node artifacts on graph edges (`complete_node` carries the typed handoff); `status`/`summary` observe the swarm |
| `swarm {action:"list_channels"\|"channel_members"\|"subscribe_channel"\|"unsubscribe_channel"}` | no replacement; group reach is the spawned subtree |
| `swarm {action:"await_members"}` | unchanged |

The daemon wire is same-binary and private, so this is a one-pass removal rather
than a deprecation window: no external producer speaks old swarm frames, and the
harness API never carried them.

## Cancellable work (protocol 1.22)

The harness API keeps major version 1 and moved from minor version 21 to 22.
Everything below is additive: a client that sends none of the four requests
reads the same frames it did before, and every event it already knew decodes
unchanged.

The daemon already did all four things for its own clients. The gap was the
harness API: an SDK or desktop client could start a turn, a tool call and a
background terminal, and could not stop any of them or ask what was still
running. This version puts those four operations on the socket, gated behind
one capability.

| Capability | Surface it gates |
| --- | --- |
| `cancellable_work_v1` | `cancel_turn`, `cancel_tool_call`, `cancel_background_terminal`, `list_background_work`, and the three reply events below |

The bridge advertises `cancellable_work_v1` unconditionally, like every other
gated capability, so a client can check it before sending. Whether the request
can actually run depends on the daemon behind the bridge: it must advertise
`cancellable_work_api` in its own capability list. A daemon that does not is
answered `unsupported` naming `cancellable_work_v1`, not `unknown_request`,
because the request is valid for this protocol version and the cause is the
build behind the socket. The bridge can only forward these four requests when
the daemon serves them, and refusing beats writing a frame an older daemon
would silently drop, which would park the client until its own timeout.

### Requests

| Request | Fields | Meaning |
| --- | --- | --- |
| `cancel_turn` | `session_id`, `run_id` | Stop the run the caller saw start, and only that run |
| `cancel_tool_call` | `session_id`, `call_id` | Stop one tool call while the turn keeps running |
| `cancel_background_terminal` | `session_id`, `call_id` | Stop one background terminal this session started |
| `list_background_work` | `session_id` | The work still running in this session |

`cancel` already existed and stops whatever turn is running. `cancel_turn`
names the run id a client observed, so a cancel that loses the race with a
finished turn cannot reach the successor turn. `run_id` and `call_id` must not
be empty; an empty value is refused as `invalid_request` before anything is
forwarded.

A cancelled tool call still reports a `tool_done`, and the cancelled turn
reports its own stop, so the transcript stays valid and the model sees a result
for every call it made. A background task's stop is confirmed by its final
`background_work` event, not by the reply: the reply only says a cancellation
was accepted.

Two ordering rules hold on the daemon's side of the socket. A finished turn is
closed before the next `message` for that session is read, so a client that
answers a turn's terminal event with its next prompt is not refused with
`Already processing a message` (`crates/app-core/src/server/client_lifecycle.rs:824-834`).
A `no_reply` message answered with that terminal event is a context message: it
starts no turn, so it waits out the finished turn's completion tail, is stored
exactly once and answered with `context_message_added`. Only a turn that is
really running - this connection's own, or one any surface registered - answers
the busy error, and it answers it at once.
And a cancel's `Interrupted` and the turn's `Done` are written only after the
cancelled turn's own frames have been forwarded, waiting at most 500 ms for
that (`crates/app-core/src/server/client_lifecycle.rs:4026-4036`,
`crates/app-core/src/server/fanout_flush.rs:56-60`).

### Events

```json
{"v":1,"reply_to":10,"ev":"cancel_turn_result","session_id":"s-1","run_id":"run-7","accepted":true}
{"v":1,"reply_to":11,"ev":"tool_call_cancel_result","session_id":"s-1","call_id":"call-3","accepted":false,"reason":"final"}
{"v":1,"reply_to":12,"ev":"background_work_list","session_id":"s-1","items":[{"call_id":"call-4","task_id":"bg_9","kind":"terminal"}]}
```

| Event | Fields |
| --- | --- |
| `cancel_turn_result` | `session_id`, `run_id`, `accepted`, optional `reason` |
| `tool_call_cancel_result` | `session_id`, `call_id`, `accepted`, optional `reason` |
| `background_work_list` | `session_id`, `items` |

Every reply echoes the `run_id` or `call_id` it answers. The daemon's frames are
broadcast to the connection without per-request correlation, so without the echo
a client with two cancels in flight could match the wrong reply.

The echo comes from the daemon, so a bridge speaking to a daemon that predates
it answers no reply for that frame instead of a reply with an empty subject: the
client sees its own request timeout, which names a cause it can act on, rather
than a verdict that belongs to another request.

`reason` is absent when the cancellation was accepted, and names the refusal
otherwise.

| Value | Meaning |
| --- | --- |
| `unknown` | The session is not running that run, or does not know that call |
| `final` | The call already ended |
| `not_cancellable` | The call exists but cannot be stopped through this request |

A `background_work_list` item carries `call_id`, `task_id`, `kind`,
`command`, `cwd` and `output`. `kind` is `terminal` or `tool_call`. The last
three are absent when they do not apply, and `output` is the last 64 KiB of what
the task has produced so far, base64-encoded. Only work a tool call started is
listed; daemon housekeeping has no call id and no editor-side home.

The bridge re-decodes each item field by field rather than passing the daemon's
object through, so a field a future daemon adds is dropped instead of reaching a
client that cannot read it.

### Client compatibility

- The three events are new names. A client that predates them skips them, as it
  skips any unknown event, and the round trip of every older frame is covered by
  `schema_snapshot_tests::older_event_frames_still_decode_after_the_enum_grew`.
- A `cancel_turn` reply still arrives after the existing `ok` acknowledgement
  that `cancel` has always answered with, so a client waiting on the
  acknowledgement is unaffected.
- The SDKs expose the four operations as `cancel_turn` / `cancelTurn`,
  `cancel_tool_call` / `cancelToolCall`, `cancel_background_terminal` /
  `cancelBackgroundTerminal` and `list_background_work` /
  `listBackgroundWork`, and each refuses before writing to the socket when the
  capability is absent.

### Sources

- Request definitions: `CancelTurn`, `CancelToolCall`, `CancelBackgroundTerminal` and `ListBackgroundWork` in `crates/harness-api/src/requests.rs`
- Event definitions: `CancelTurnResult`, `ToolCallCancelResult`, `BackgroundWorkList`, `ToolCallCancelOutcome` and `BackgroundWorkItem` in `crates/harness-api/src/events.rs`
- Implementation: `crates/app-core/src/server/background_work.rs`, `crates/app-core/src/server/tool_cancel.rs`, `crates/app-core/src/server/client_lifecycle.rs`
- Capability constants: `CAPABILITY_CANCELLABLE_WORK_V1` in `crates/harness-api/src/lib.rs`, `cancellable_work_api` in `crates/app-core/src/server/session_connections.rs`
- Protocol version: `API_VERSION_MAJOR = 1`, `API_VERSION_MINOR = 22`

## Daemon effective settings (protocol 1.25)

The harness API keeps major version 1 and moved from minor version 24 to 25.
Everything here is additive: a client that never sends the request reads the
same frames it did before.

A settings screen that shows only the client's own preferences cannot explain
why a turn behaves the way it does. `get_effective_settings` reports a **fixed
allow-list** of daemon values, each with the layer that supplied it. It is a
list, not a dump: there is no "other keys" field and no raw file text, so a
credential in the config file cannot reach a client however the file is
written. `effective_settings_v1` gates the pair.

### Request: `get_effective_settings`

```json
{"v":1,"id":7,"req":"get_effective_settings","session_id":"s-1"}
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | Yes | Session the question is about |

### Response: `effective_settings`

```json
{"v":1,"reply_to":7,"ev":"effective_settings","session_id":"s-1",
 "settings":[{"key":"provider.stream_idle_timeout_secs",
              "label":"Stream idle timeout (seconds)",
              "value":"240","source":"file","origin":"/home/u/.horon/config.toml"}]}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `key` | string | Dotted config path, e.g. `provider.stream_idle_timeout_secs` |
| `label` | string | Human-readable name for the row |
| `value` | string | The value in force, as the screen prints it |
| `source` | `default`, `cli`, `file`, `env` | The layer that supplied it |
| `origin` | string, absent for `default` | The flag, file path or variable name `source` points at |

`value` is text because the screen prints it: a client that rendered a number
itself would have to know which keys are numeric, and that knowledge belongs
beside the allow-list rather than in every client.

### Allow-list

The rows are `provider.openai_reasoning_effort`,
`provider.anthropic_reasoning_effort`, `provider.stream_idle_timeout_secs`,
`provider.max_retries`, `tools.profile`, `tools.mcp_tools`,
`tools.approval_mode`, `tools.ask_policy`, `tools.secrets_mode`,
`compaction.mode`, `messages.{follow_up,steering,interrupt}_mode`. A key added
to the daemon's spec table is the only way a row appears; nothing outside it
can be reported.

### Behaviour

The **daemon** answers, from the configuration it actually loaded. It is the
process whose environment, launch flags and config file the session runs with,
so it is the only process that can say which value is in force and where that
value came from. The bridge only translates: it forwards
`get_effective_settings` on the internal protocol and passes the rows back.
`crates/base/src/effective_settings.rs` holds the table and the source
decisions; `crates/app-core/src/server/effective_settings.rs` maps the rows onto
this reply.

A daemon advertises `effective_settings_api` in its ping. The bridge advertises
`effective_settings_v1` unconditionally and refuses the request with a
structured `unsupported` naming that capability when the daemon behind it does
not advertise it — an older daemon answers an unknown request with a frame that
carries no id, so a forwarding bridge would otherwise leave the client waiting
for its own timeout. A client sees the same "this daemon does not report its
settings" state from an older bridge (which never advertises the capability) and
from an older daemon (which is refused by name).

The layer is decided from evidence, strongest first:

1. `cli` — a flag the launcher recorded for the variable it set. The launcher
   turns flags such as `--tool-profile` and `--mcp-tools` into environment
   variables, so the environment alone cannot tell a flag from a variable the
   user exported. A default the launcher chose because nothing selected one is
   not reported at all: the variable exists, but the user never set it.
2. `env` — a variable this process read and the daemon would apply. A variable
   the daemon ignores (a zero timeout, an unparseable retry count, a mode it does
   not know) is not named as the source of the value in force.
3. `file` — the effective config file: the same strict parse the daemon runs,
   read as one document, and only when the declared value is one the daemon
   applies and renders the value in force. A file that does not parse supplied
   nothing, so its rows read as `default`, and neither does a declared value the
   daemon rejects — `approval_mode = "nonsense"`, for example, falls back to the
   default without making the file the source of that default.
4. `default` — the shipped value.

The rows describe the daemon's own configuration. A session that changes a value
for itself at runtime (for example `set_session_approval_mode`) is not reflected
here; the row reports what the daemon loaded, not what one session overrode
afterwards.

Nothing writes. The request is read-only by construction, and a client that
cannot read it keeps working against the daemon defaults. The SDKs expose the
call as `get_effective_settings` (Rust, Python) and `getEffectiveSettings`
(TypeScript); each refuses it before sending when the capability was not
advertised. The TUI's `Daemon` tab is the shipped consumer.

## Session event store and replication (protocol 1.12)

The harness API keeps major version 1 and moved from minor version 11 to 12. Everything below is additive. A client that sends only the requests it already sent keeps working, and reading the conversation history still needs no new request.

A client negotiates the handshake and checks the capabilities it needs before sending anything. Alongside the existing set, the bridge advertises the following.

| Capability | What it controls |
| --- | --- |
| `session_event_store_v1` | `list_session_heads`, `select_session_head` |
| `session_replication_v1` | `export_session_events`, `import_session_events`, `export_session_blob`, `import_session_blob`, `get_session_blob_status`, and the whole-record blob pair |
| `session_history_cursor_v1` | `get_history_page` |
| `structured_compaction_v1` | Reading the structured summary fields of a `compacted` record. No method is gated by this capability |

A request sent without the capability is answered `unsupported` with the missing capability name. That is not a version error. Either update and restart both the daemon and the bridge, or stop using that method against this build.

### Heads

A session holds several heads after a branched import or after a turn is appended to a rewound branch. A rewind alone adds none: it writes no event, it records a selection over the graph that is already there, so the log keeps its single tip. The selected head is **host-local**. It is not replicated and is not part of the session's permanent identity. `list_session_heads` reports the heads and the current selection, and `selected_head` is absent when the several heads need an explicit choice. Until one is selected, execution is refused, and `select_session_head` answers `busy` when another process holds the write lock. Because the choice changes what the user's next turn continues from, never pick one silently; show the choice to the user.

### History

`get_history` is unchanged and still returns the whole visible conversation history. A history row keeps `content` exactly as before; when a stored assistant row also carries a reasoning trace, it adds an `answer` field with the visible text blocks joined, so a client that needs the answer itself does not have to interpret the daemon's reasoning markup. Rows without reasoning omit the field. A row may also carry `message_id`, the session's stored id of the message it was rendered from: the bridge asks the daemon for those ids, so it is present on rows from a daemon that reports them and absent on synthetic rows and on rows from an older daemon. `get_history_page` is the bounded read a UI wants on long sessions. It takes `session_id`, an optional `head_event_id` (defaulting to the selected head), the opaque continuation value `before_event_id`, and `limit` (default 50, maximum 200). The response is a `SessionHistoryPage` with a fixed `head`, a list of page messages from oldest to newest, and a `next_cursor` to pass back as `before_event_id`. Pin `head_event_id` while the user scrolls. A cursor with a pinned head points at the same history even after the selection changes.

### Replication

`export_session_events` returns the origin for a pinned head, one bounded page at a time with parents first. `import_session_events` validates the whole page before committing and answers with `accepted_ids`, `heads`, `retry_cursor` and `conflict_heads`. Original blobs move separately in 1 MiB chunks and are verified by SHA-256 and size before publication. An interrupted transfer continues from `get_session_blob_status`.

### Markdown transcript

`export_session_markdown` takes `session_id` and replies with a `session_markdown` event carrying the whole readable transcript in `markdown`. Each turn is a `### User` or `### Assistant` heading followed by its content: text verbatim, a tool call as a fenced JSON block, a tool result as a fenced block, and an image or audio block as a short placeholder. Secrets are redacted with the same pattern table the disk path uses, so a token that never reached the event log cannot appear in the transcript. A tool result longer than 4 KiB is cut at a UTF-8 boundary and replaced with a `… (truncated, N bytes total)` marker.

The reply is not part of the replication protocol and needs no `protocol_version`. It requires `session_replication_v1`, the capability that already gates the other stored-session reads. An unknown session answers `unknown_session`, the same error the other reads use. `horon export <session-id> [--out <path>]` writes identical bytes, because both call one renderer.

### HTML report (protocol 1.27)

`export_session_html` takes `session_id` and replies with a `session_html` event carrying a standalone document in `html`. It renders the same redacted projection as `export_session_markdown`, so a secret or a truncated tool result is identical in both formats; the difference is the presentation. Each turn is a `<section>` with an `<h2>` naming the role, its text in `pre-wrap` blocks that keep the line breaks, and a tool call or result in a `<pre>` block.

The document is meant to be saved and opened later without a connection. Every transcript character is escaped, so stored text that looks like markup renders as characters instead of becoming a node; the stylesheet is inline, with no font, image or script reference; and the head carries `<meta http-equiv="Content-Security-Policy" content="default-src 'none'; style-src 'unsafe-inline'">`, which makes a browser refuse any network load the document might later gain. It requires `session_replication_v1` and answers `unknown_session` for an id the store does not hold.

`horon export <session-id> --html [--out <path>]` writes the same bytes, and `--json` wraps them as `{"session_id": ..., "html": ...}`. Unlike the Markdown form, an `--out` path that already exists is refused rather than overwritten: a report is a destination the reader named by hand.

Two rules a client must not break:

- **Never re-serialize `canonical_json`.** An event's canonical JSON travels as a string. `u64` values above 2^53, `1.0` and `-0.0` do not survive a round trip through JavaScript numbers. Pass the string through untouched.
- **Treat `conflict_heads` as data.** Branched heads are all preserved. No timestamp decides a winner, and an import must not discard a branch the user did not choose.

Re-sending an import is safe. The same id with the same hash does nothing.

### Errors

The five stable `ErrorCode` values are unchanged, so older clients keep decoding them. A finer cause comes in an optional `details` object. It carries `store_code` (for example `hash_conflict`, `missing_dependency`, `conflict_heads`, `busy`, `invalid_cursor`, `record_too_large`), `retryable`, `accepted_ids`, `retry_cursor` and `conflict_heads`. Ignore `details` when you do not use it. Branch on `retryable` before retrying, and never retry a `hash_conflict` unchanged.

### Status

`runtime_info` builds liveness from the current host runtime. A PID recorded in stale session metadata is historical side information, not a live process, and no client should display it as running.

### Runtime identity fields

`get_runtime_info` answers with the session's identity. Two of its fields exist because the model that answered a turn is not always the model the session selected.

| Field | Type | Meaning |
|---|---|---|
| `fallback_models` | `array<string>` | Fallback model ids the active named provider profile is configured with, in the order a turn tries them. The key is absent when the list is empty. |
| `serving_model` | `string` | Model that produced the most recent assistant response. After a fallback answered it differs from `model`, which returns to the session's own selection once the turn ends. Absent when no response has been named yet. |

Both fields are optional. An older daemon omits them, and a client that ignores them keeps working. Once the catalog and one identity report have arrived, the bridge answers `get_runtime_info` from its cache when no fallback list is configured, because the serving model can then only be the session's own. With a fallback list configured, or before the first identity report, it asks the daemon for the catalog on every `get_runtime_info`, because the serving model can change without the catalog changing.


### Connection lifetime after a client leaves

A bridge serves an API connection for as long as the client's socket is open, and
it holds one daemon connection for that client. When the client goes away the
bridge closes its daemon leg and keeps listening on the socket; only a bridge
that fails to bind or loses its listener exits.

The client half of that rule is easy to get wrong in a test harness: splitting a
socket into read and write halves does not make each half an independent
connection, so dropping only the write half leaves the stream open, no FIN
reaches the bridge, and the bridge keeps its daemon leg. Both halves have to go.
This is a harness mistake rather than a bridge defect, and it is why
`crates/harness-api-server/tests/v1_client_round_trip.rs` drops both halves and
bounds its daemon-leg read: a bridge that keeps the leg open after its client
left now fails the assertion instead of hanging the target until the runner's
timeout.

The full storage format, limits and legacy migration rules are in `docs/protocol/SESSION_STORE.md`.

## Ask requests a client declares in the handshake

The `ask` tool shows a person a question and waits for the answer. The daemon draws no screen and cannot assume a client is attached, so the question goes only to a connection that said it can show one. The advertisement is one boolean field on `Hello`:

| Field | Type | When absent | Meaning |
| --- | --- | --- | --- |
| `supports_ask_requests` | boolean | `false` | This connection draws the `ask` tool's questions and answers them |

The bridge reads the field with `hello["supports_ask_requests"].as_bool().unwrap_or(false)` (`crates/harness-api-server/src/lib.rs`), so a client that predates the field advertises nothing and keeps working. The field is not a capability string and not a protocol-minor negotiation: it gates the direction the person is asked in. A session whose attached connection advertised it gets the question there and the call waits for the answer; a session without such a connection falls back to `ask_policy` (`docs/safety/SAFETY.md`).

The SDKs expose it as one connect option, and all three default it to off:

| SDK | Option | Default |
| --- | --- | --- |
| Rust | `ConnectOptions::supports_ask_requests` | `false` |
| TypeScript | `supportsAskRequests` | `false` |
| Python | `supports_ask_requests` | `False` |

The Rust SDK copies the option into `Hello` (`crates/agent-sdk/src/client.rs`), TypeScript writes `options.supportsAskRequests ?? false` and Python passes the field straight through. The TUI binary `horon-tui` sets it to `true` in `connect_options` (`crates/tui/src/lib.rs`), because it draws the question and answers it. A client that only runs turns leaves the default in place, and a turn that reaches `ask` then resolves through the policy instead of parking on a question nobody can see.

## Harness API request and event surfaces: usage_report, search_sessions, list_artifacts, durable_runtime

This document records the request surfaces added to the harness API. The first part covers the three requests of protocol 1.13 and their response events, the next covers the four durable runtime surfaces of 1.14, and the part after that covers the argument repair of 1.16. Field names and types are copied from the definitions in `crates/harness-api/src/requests.rs` and `crates/harness-api/src/events.rs`, and behaviour and limits are the values confirmed in the implementation under `crates/harness-api-server/src/translate/`.

All three requests are additive. A client that sends none of them keeps working, and the bridge advertises `usage_report`, `session_search` and `artifacts` in the `capabilities` of `hello_ok` (`BRIDGE_CAPABILITIES` in `crates/harness-api-server/src/lib.rs`).

`approval_ack` and `failover_ack` follow `list_artifacts`. Both are acks a client sends to retire a durable approval or failover announcement, so neither is behind a capability of its own: a daemon that does not know the ack answers it with an error instead of ignoring it.

### Common rules

- One frame is one JSON object on one line (NDJSON). A request names its kind in `req` and carries an `id`, and a response echoes that `id` in `reply_to`.
- Request bodies serialize with `#[serde(tag = "req", rename_all = "snake_case")]`, so field names are snake_case.
- Unknown fields are ignored, and unknown event kinds are skipped.
- A failure arrives as `{"ev":"error","code":...,"message":...}`. The `ErrorCode` values these surfaces use are `invalid_request`, `unknown_session` and `internal`.
- A request that names a session takes `session_id`. A missing session answers `unknown_session` rather than an empty result, because "this session wrote nothing" and "no such session exists" are different facts.
- `session_id` also accepts a unique leading prefix of at least 6 characters. A full id always wins, and an id the connection already knows is never rewritten. A prefix several sessions share answers `unknown_session` with up to 10 candidates in `details.accepted_ids` and `details.store_code` set to `ambiguous_session`; the code itself stays `unknown_session`, so a client built against an older build still decodes the frame. A prefix that matches nothing keeps the plain `unknown_session` answer.

### usage_report

Returns token usage, the context window and per-model totals for the attached session and for every stored session. The limits field (`limits`) remains but this build has no source for it, so it is always an empty array. The capability name is `usage_report`.

#### Request

```json
{ "v": 1, "id": 7, "req": "usage_report", "session_id": "session_..." }
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | No | Narrows the report to this session. Omitted, it reports every stored session together with the attached session |

An unknown `session_id` is `unknown_session`.

#### Response: `usage_report`

```json
{
  "v": 1,
  "reply_to": 7,
  "ev": "usage_report",
  "session_id": "session_...",
  "sessions": [],
  "totals": {},
  "models": [],
  "context_window": 200000,
  "limits": [],
  "pricing": "unknown",
  "estimated_cost": null
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `session_id` | string, may be absent | The session the report was narrowed to. Absent in a full report |
| `sessions` | `UsageSession[]` | One row per session in scope, ordered by session id |
| `totals` | `UsageTotals` | The sum across `sessions` |
| `models` | `UsageModel[]` | Per-model totals, ordered by model id |
| `context_window` | number, may be absent | Context window (tokens) of the attached session's active route. Absent means "unknown", not another model's default window |
| `limits` | `UsageLimitInfo[]` | The limit list. This build has no account source that reports limits, so it is always an empty array |
| `pricing` | string | Always `"unknown"`. This repository has no price table |
| `estimated_cost` | number, may be absent | Always `null`. With no price table there is no cost estimate either |

`UsageSession`:

| Field | Type | Meaning |
| --- | --- | --- |
| `session_id` | string | Session id |
| `model` | string, may be absent | The model the session metadata recorded |
| `input` | number, may be absent | Sum of input tokens. Absent when no request recorded any |
| `output` | number, may be absent | Sum of output tokens |
| `cache_read_input` | number, may be absent | Sum of cache-read input tokens |
| `cache_creation_input` | number, may be absent | Sum of cache-write input tokens |
| `requests` | number | Provider requests that recorded usage. Not the number of user turns; one turn issues several requests and each tool round trip counts separately |

`UsageTotals` holds `input`, `output`, `cache_read_input` and `cache_creation_input` (each may be absent), plus `requests` and `sessions` (the number of sessions the sums cover, including sessions without usage).

`UsageModel` holds `model` (`unknown` for a session whose metadata named no model), the same four token sums, `requests` and `sessions`.

`UsageLimitInfo` holds `name`, `used`, `limit`, `unit` (for example `usd`) and `resets_at` (RFC 3339). `used`, `limit` and `resets_at` are present only when the daemon reported them.

#### Behaviour

The report merges three sources in order of authority: the attached session's daemon counters, the `token_usage` records in the stored session source, and the last live `token_usage` event. A metric no request recorded is `null`, not `0`, because a provider not reporting cache tokens and a provider reporting zero are different facts.

This build has no account subscription, so the daemon reports no limits and `limits` is always an empty array. An empty array means "this build has no limit source", not "this account has no limits".

The three SDKs send it as `usage_report(session_id: Option<&str>)` in Rust, which returns a `UsageReport`, `usageReport` in TypeScript and `usage_report` in Python.

### search_sessions

Searches the transcripts of every stored session, not just the attached one. The capability name is `session_search`. It is needed because filtering to sessions with a session switcher cannot answer "where was that conversation".

#### Request

```json
{ "v": 1, "id": 8, "req": "search_sessions", "query": "zanzibar", "limit": 10 }
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `query` | string | Yes | Search term. Whitespace only is `invalid_request` |
| `limit` | number | No | Maximum hits. Default 20, capped at 50 |

`query` is not interpreted as a path, a glob or a SQL fragment. It is searched as the literal string. A `limit` of 0 returns an empty result.

#### Response: `session_search_results`

```json
{
  "v": 1,
  "reply_to": 8,
  "ev": "session_search_results",
  "query": "zanzibar",
  "results": []
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `query` | string | Echoes the request's search term, so a client that sent several searches can tell which answer is on screen |
| `results` | `SessionSearchHit[]` | The hits |

`SessionSearchHit`:

| Field | Type | Meaning |
| --- | --- | --- |
| `session_id` | string | Stored session the hit belongs to |
| `title` | string, may be absent | The display title of that session |
| `role` | string | `user`, `assistant`, or `metadata` for a title or session-level hit |
| `preview` | string | Plain-text excerpt cut around the match. Cut spans are marked with `...` |
| `at` | string | RFC 3339 time of the matching message. For a metadata hit, the session time |

#### Behaviour

It uses the same engine, the same index and the same scoring as the agent's own session search, so a search from the agent and a search from a client return the same results. With no storage directory the result is empty, and an engine failure is `internal`.

The three SDKs send it as `search_sessions(query, limit: Option<u32>)` in Rust, `searchSessions` in TypeScript and `search_sessions` in Python.

### list_artifacts

Lists the files a conversation produced: images the conversation carried in, and HTML and image files written into the working directory after the session started. The capability name is `artifacts`.

#### Request

```json
{ "v": 1, "id": 9, "req": "list_artifacts", "session_id": "session_..." }
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | Yes | Session to list. Missing, or with no stored record, it is `unknown_session` |

#### Response: `artifacts`

```json
{
  "v": 1,
  "reply_to": 9,
  "ev": "artifacts",
  "session_id": "session_...",
  "artifacts": []
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `session_id` | string | The requested session |
| `artifacts` | `ArtifactEntry[]` | Entries, newest first |

`ArtifactEntry`:

| Field | Type | Meaning |
| --- | --- | --- |
| `path` | string | Path relative to the session working directory, with `/` separators |
| `kind` | string | `html` or `image` |
| `bytes` | number | File size at response time |
| `mtime_ms` | number | Last modification time in epoch milliseconds |

#### Behaviour

Only metadata is returned. The client reads the bytes separately with `read_file`, so even a 40 MB HTML report costs one `stat` per candidate.

The list is collected from two sources: paths named by the transcript and a scan of the working directory. Both reject paths that leave the session root and reject symbolic links, so a transcript naming `../../.ssh/id_rsa` never puts it on the list. When the session start time is not recorded, the session file's modification time stands in for it, and older files are excluded. The result is sorted by `mtime_ms` descending, by path ascending for equal times, and cut at 200 entries.

The three SDKs send it as `list_artifacts(session_id)` in Rust, `listArtifacts` in TypeScript and `list_artifacts` in Python.

### approval_ack

Retires the daemon's durable copy of an `approval_resolved` event, so a later attach or restart does not deliver it again. An approval stays parked until it is acked. This is an ack a client sends, not a surface the server originates: the reply is a bare `ok` and no event follows it. `approval_ack` in the event vocabulary names this client acknowledgement, and the daemon never emits it.

#### Request

```json
{ "v": 1, "id": 21, "req": "approval_ack", "session_id": "session_...", "request_id": "req_..." }
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | Yes | Session the approval belongs to. The connection must be attached to it |
| `request_id` | string | Yes | The `request_id` of the `approval_resolved` event |

The legacy ack frame the bridge forwards carries no session field, so an empty or missing `session_id` on an attached connection applies the ack to the attached session.

#### Response

```json
{ "v": 1, "reply_to": 21, "ev": "ok" }
```

#### Behaviour

- The connection must be attached to the session. One that never asked to attach, or that names a `session_id` other than the attached one, is `unknown_session`. That check runs before the field checks, so an empty `request_id` on an unattached connection is `unknown_session` rather than `invalid_request`.
- An empty or missing `request_id` is `invalid_request`. An ack with no identifier would clear nothing while reporting success.
- A `request_id` whose record is already gone is still answered `ok`. The runner may delete the record first and the ack arrive late, so a late ack is not a failure.
- The three SDKs send it as `ack_approval(session_id, request_id)` in Rust, which returns `()`, and as `ackApproval` in TypeScript and `ack_approval` in Python, which wait for the `ok` and return a receipt built from the values that were sent.

### failover_ack

Echoes a `failover_switched` announcement so the daemon can clear it. The whole announcement key travels, because a partial key would either clear nothing or read as a different switch.

#### Request

```json
{ "v": 1, "id": 22, "req": "failover_ack", "session_id": "session_...", "chain_id": "chain_...", "from": "model-a", "to": "model-b", "attempt": 1 }
```

| Field | Type | Required | Meaning |
| --- | --- | --- | --- |
| `session_id` | string | Yes | Session the announcement belongs to. The connection must be attached to it |
| `chain_id` | string | Yes | The switch chain the announcement belongs to, non-empty |
| `from` | string | Yes | Model the chain switched away from, non-empty |
| `to` | string | Yes | Model the chain switched to, non-empty |
| `attempt` | number | Yes | Attempt number of this switch, a non-negative integer |

#### Response

```json
{ "v": 1, "reply_to": 22, "ev": "ok" }
```

#### Behaviour

- The connection must be attached to the session, with the same `unknown_session` answer and the same ordering before the field checks as `approval_ack`.
- An empty or missing `chain_id`, `from` or `to` is `invalid_request`. So is a missing `attempt` or one that is not a non-negative integer.
- A key the daemon holds no announcement for is still answered `ok`. A key that differs in any part clears nothing, which is why the client echoes all five values.
- The three SDKs send it as `ack_failover(session_id, chain_id, from, to, attempt)` in Rust, which returns `()`, and as `ackFailover` in TypeScript and `ack_failover` in Python, which wait for the `ok` and return a receipt built from the values that were sent. The Python argument is spelled `from_` because `from` is a keyword; the wire key stays `from`.

### durable_runtime_v1 · monitor_v1 · snapshot_marker_v1 · ask_receipts_v1

The four surfaces added by protocol minor 14. All four are **additive**, so a client that did not negotiate the capability neither sends nor receives these requests. Existing clients behave as before.

| Capability | Requests and events it opens | What it guarantees |
| --- | --- | --- |
| `durable_runtime_v1` | `get_runtime_state`, `apply_control`, `get_control_receipt` | Run state that survives a restart, and control receipts where a resend of the same operation id is applied only once |
| `monitor_v1` | File and command monitors of the `monitor` tool | Survives a restart as `needs_rearm` without re-running the command |
| `snapshot_marker_v1` | `get_snapshot` | `SnapshotMarker` arrives 1:1 immediately before `Snapshot`, and the `seq` of live events continues after it |
| `ask_receipts_v1` | `answer_id` of `ask_response` | The same `question_id`+`answer_id`+`digest` replays the stored result, and a different digest is a conflict |

#### Boundary rules

- A `SnapshotMarker` and a `Snapshot` never go to different connections. Only the connection that received the marker receives the snapshot.
- Live events after a snapshot carry a `seq` issued by the observation owner. A client can prove "everything after N is newer" itself instead of guessing order.
- `apply_control` has the server build the fingerprint. The same id with the same fingerprint replays the stored result, the same id with a different fingerprint is `conflict`, and a concurrent `applying` is `pending` without a second execution. Anything still applying at restart is sealed as `indeterminate` and never executed again. Invalid `apply_control` arguments (empty `operation_id`, empty `expected_run_id`, or empty `input_ids`) fail with `invalid_request`.
- Concurrent `create_session` and `attach_session` calls on one bridge connection keep separate wire correlation ids instead of overwriting an earlier in-flight attach.
- An operation id outside the retention window is `unknown`. The SDK never retries automatically in that case.
- The only supported actions are `abort_run(expected_run_id)` and `cancel_inputs(input_ids)`. Model changes, files, shells and arbitrary commands are not on this surface.
- A request against a capability the bridge does not advertise is unreachable. That is why all four strings are in `BRIDGE_CAPABILITIES`.
