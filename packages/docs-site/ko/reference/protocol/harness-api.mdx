데스크톱·SDK 클라이언트가 로컬 소켓으로 쓰는 하네스 API의 자격 증명 설정과 요청·이벤트
표면을 다룬다. 로컬 소켓은 Unix 소켓이거나 Windows의 네임드 파이프이며, 두 방식은 같은
프레임을 나른다. 소켓 경로에서 응답이 없으면 클라이언트가 `horon-agent api-bridge`를 직접
띄우고 그 경로에서 기다린다. 그래서 브리지는 SDK가 지원하는 모든 플랫폼에서 에이전트
바이너리의 하위 명령이다.

클라이언트는 읽기와 쓰기를 동시에 할 수 있다. SDK 클라이언트는 다음 프레임을 읽는
스레드를 하나 붙잡아 두고 다른 스레드로 요청을 쓰며, Windows의 파이프는 겹친 입출력
(overlapped I/O)으로 열려 대기 중인 읽기가 쓰기를 막지 않는다.

## 자격 증명 설정

이 빌드에는 대화형 로그인 흐름이 없다. SDK가 자격 증명에 대해 노출하는 것은 둘이다.

- `HoronAgentClient::set_api_key(provider, key)` (TypeScript `setApiKey`)는 키를
  horon-agent의 소유자 전용 자격 증명 저장소에 쓰고(`SetApiKey` 요청,
  `credential_updated` 응답) 프로바이더 자격 증명을 다시 읽는다. 키는 응답이나 로그에
  남지 않는다.
- `notify_auth_changed(provider)` (TypeScript `notifyAuthChanged`)는 사용자가 다른
  도구로 OAuth에 로그인한 뒤 갱신된 자격 증명 파일을 다시 읽으라는 알림이다. 자격 증명
  자체를 보내지 않으며 브리지는 `auth_changed_notification`으로 이 기능을 광고한다.

OAuth 토큰은 SDK가 발급하거나 갱신하지 않는다. 런치 옵션 `inherit_logins`(기본 켜짐)가
사용자의 기존 CLI 자격 증명 파일을 인스턴스에 연결하고, 모델 요청은 그 파일을 그대로
쓴다(`crates/agent-sdk/src/launch.rs`). 모델 호출은 `[providers.<name>]`의 OpenAI 호환
프로파일로만 나가므로, 이 빌드에는 OAuth로 인증하는 모델 런타임이 없다. `openai-oauth:`
접두사는 남아 있지만 그 런타임이 없어 호출 전에 실패한다(`docs/provider/MODEL.ko.md`).

## 내구성 런타임 API(프로토콜 1.14)

주 버전은 `1`에 머물고 부 버전이 13에서 14로 올랐다. 아래 표면은 모두 추가형이다.
기존 요청의 바이트 표현과 응답 모양은 바뀌지 않았고, 새 요청을 보내지 않는 클라이언트는
이전과 똑같이 동작한다.

브리지는 다음 네 기능을 광고한다. 클라이언트는 무엇이든 보내기 전에 확인한다.

| 기능 | 게이트하는 표면 |
| --- | --- |
| `durable_runtime_v1` | `get_runtime_state`, `apply_control`, `get_control_receipt` |
| `monitor_v1` | 없음. 감시는 기존 도구 호출로 시작하고 멈추므로 결과를 어떻게 읽을지 알려 주는 표시다 |
| `snapshot_marker_v1` | `get_snapshot`과 `snapshot_marker` 이벤트 |
| `ask_receipts_v1` | `ask_response`의 선택적 `answer_id` |

기능 없이 보낸 요청은 빠진 기능 이름을 담은 구조화된 `unsupported` 오류로 거부된다.
성공으로 처리되지 않고, 버전 오류도 아니다. 두 SDK는 같은 이름의 메서드
(`get_runtime_state`/`getRuntimeState`, `apply_control`/`applyControl`,
`get_control_receipt`/`getControlReceipt`, `get_snapshot`/`getSnapshot`,
`respond_to_ask_with_id`/`respondToAskWithId`)를 제공하며, 기능이 없으면 요청을 소켓에
쓰기 전에 거부한다. 구서버가 알 수 없는 요청을 받아 잘못 처리하는 일을 막는 지점이다.

### 상태 요약

`get_runtime_state`는 세션의 내구성 저널에서 실행·대기열·영수증·감시를 **요약**해 돌려준다.
접수된 입력 본문, 명령 인자, 명령 환경변수는 여기에 실리지 않는다. 상태 판넬에 필요한 것은
개수·단계·원인이지 대기열에 든 문장이 아니다.

| 필드 | 뜻 |
| --- | --- |
| `journal` | 저널 존재 여부, 세대, 마지막 seq, 바이트, 레코드 수, 읽기 전용 여부 |
| `runs` | 아직 끝나지 않은 실행. `run_id`, `started_at`, 선택적 `input_id` |
| `queue` | 살아 있는 입력 수, 결과가 확정되지 않은 입력 수, 보유 바이트 |
| `receipts` | 완료·취소된 입력 영수증(최근 것부터). `input_id`, `phase`, `seq` |
| `monitors` | 감시 id, 종류, 중지 여부, 마지막 체크포인트 요약 문장 |
| `pending_wakes` | 전달되지 않은 깨우기 수 |
| `pending_controls` | 아직 끝나지 않은 제어 수 |
| `last_stop` | 마지막 실행이 끝난 원인과 시각 |

### 제어와 영수증

`apply_control`은 호출자가 정한 `operation_id`로 제어 동작을 적용한다. 같은 id를 다시 보내면
기록된 영수증을 돌려주고 동작을 두 번 적용하지 않는다. `get_control_receipt`는 그 기록을 읽는다.
`outcome`은 `applying`, `terminal`, `replay`, `conflict`, `unknown`, `indeterminate` 중
하나다. `indeterminate`는 동작이 시작됐지만 종료 기록을 남기지 못해 결과를 알 수 없다는 뜻이며,
자동으로 재시도하지 않는다.

### 스냅샷과 마커

`get_snapshot`은 상태와 제한된 기록 꼬리를 하나의 일관된 시점으로 돌려준다. 응답 직전에 같은
연결로 `snapshot_marker` 이벤트가 먼저 도착하며, 두 프레임의 `marker_id`가 같다. 그 뒤에
도착한 실시간 이벤트는 모두 그 스냅샷보다 새것이다. 마커는 `reply_to`가 없는 스트림
이벤트이므로 클라이언트는 도착 순서를 추측하지 않고 경계를 분류할 수 있다. `generation`은
재시작마다 바뀌며 과거 `seq`의 재생을 약속하지 않는다.

`get_snapshot`은 `tail`(기본 20, 최대 100)과 `max_bytes`(기본 262,144, 최대 1 MiB)를 받고,
예산이 꼬리를 자르면 `truncated`가 참이 된다.

### 답변 영수증

`ask_response`에 선택적 `answer_id`가 붙었다. 같은 `ask_id`에 같은 `answer_id`와 같은 답을
다시 보내면 한 번 답한 것으로 처리되므로, 응답을 잃은 뒤의 재시도가 질문을 두 번 해결하지
않는다. 같은 질문에 다른 `answer_id`를 보내면 충돌이다. `answer_id`를 보내지 않는 기존
경로는 그대로 동작하며 기능 협상도 필요하지 않다.

### 새 이벤트

`runtime_state`, `control_receipt`, `snapshot_marker`, `snapshot` 네 가지가 추가됐다.
모두 기능으로 게이트되며, 그 기능을 협상하지 않은 연결에는 서버가 보내지 않고 SDK도 받은
뒤 버린다. 기존 연결의 바이트 수준 동작은 바뀌지 않는다.

### 응답이 만들어지는 곳

네 요청은 모두 실제로 처리된다. 데몬이 `pong`에서 `durable_runtime_api`를 알리고(`crates/app-core/src/server/session_connections.rs`) 세션과 취소 신호, 제어 원장을 소유하므로, 브리지는 요청을 데몬의 프레임으로 번역하고 응답을 되번역할 뿐이다(`crates/harness-api-server/src/translate.rs`). 데몬은 이 요청을 `crates/app-core/src/server/client_lifecycle.rs`에서 분기하고, 스냅샷은 세션의 관측 소유자로 만든다(`crates/app-core/src/server/runtime_state_api.rs`).

그래서 `unsupported`는 **이 데몬이 구버전이라는 뜻**이지, 기능이 구현되지 않았다는 뜻이 아니다. 브리지는 접속한 데몬이 `durable_runtime_api`를 알리지 않았을 때만 `durable_runtime_v1`을 지목한 이 응답을 돌려준다. 구버전 데몬은 모르는 요청에 id가 없는 오류 프레임으로 답하므로 그대로 전달하면 클라이언트가 자기 타임아웃만큼 기다린다. 클라이언트 입장에서는 다른 기능이 없을 때와 같은 "이 서버가 제공하지 않는다"는 응답이므로 분기 처리는 달라지지 않는다.

## 핸드오프 압축

`compact`는 선택 필드 `method`를 받는다. 없으면 클라이언트가 늘 요청해 온 모델 요약이고,
응답 `compacted`는 요청이 접수됐다는 뜻이다. 데몬은 다음 안전 지점에서 요약하기 때문이다.

`method: "handoff"`는 그 대신 생성한 핸드오프 문서를 경계로 쓴다. 응답은 그 쓰기가 끝난
뒤 도착하며, 접수 확인이 아니라 결과다.

요청:

```json
{"id": 4, "req": "compact", "session_id": "s-1", "method": "handoff"}
```

응답은 같은 `compacted` 이벤트에 `handoff`가 붙은 모양이다.

```json
{"id": 4, "event": "compacted", "session_id": "s-1", "message": "Committed a handoff document covering the first 120 messages.",
 "handoff": {"outcome": "committed", "covered": 120}}
```

| `handoff.outcome` | 뜻 |
| --- | --- |
| `committed` | 문서가 경계가 됐다. `covered`는 덮은 메시지 수이고 최근 토큰 꼬리는 원문으로 남는다 |
| `nothing_to_cover` | 모든 메시지가 최근 토큰 예산 안에 들어가 문서를 쓰지 않았다 |
| `provider_error` | 완성 요청이 실패했거나 문서가 거부됐다(빈 문서, `Goal` 제목 없음). `detail`에 프로바이더 메시지나 거부 이유가 온다. 대화록은 그대로다 |
| `cancelled` | 응답 전에 생성이 취소됐다. 대화록은 그대로다 |

이 필드를 게이트하는 기능은 없다. 이 필드가 없던 서버는 요청의 모르는 필드를 무시하고
`handoff` 없이 응답하므로, `method`를 보내는 클라이언트는 `handoff`가 빠진 응답을
`nothing_to_cover`가 아니라 "이 서버가 지원하지 않음"으로 다뤄야 한다. 서버가 모르는 값은
`invalid_request`로 거절한다.

요청 자체에는 취소 신호가 없다. 완성 요청 한 번이 결과를 정하므로, 기다리기를 그만둔
클라이언트가 있어도 생성은 계속된다. 이미 커밋된 경계를 되돌리지는 않는다.

## 되감기 브랜치 요약

`rewind`는 선택적 `summarize`를 받는다. 값을 빼거나 `false`로 보내면 지금까지 보내던
요청과 같고 데몬 동작도 같다.

`summarize: true`는 되감기가 버리는 브랜치의 보고서를 작성해 남는 브랜치 끝에 숨은
시스템 알림 한 개로 붙이라고 요청한다. 그러면 모델은 버려진 시도가 왜 실패했는지 알 수
있고, 대화록에는 죽은 브랜치 전체가 남지 않는다. 보고서는 무엇을 시도했는지, 무엇이 왜
실패했는지, 브랜치가 확정한 사실이 무엇인지를 담는다.

데몬의 `[compaction] rewind_summary`가 켜져 있어야 동작한다. 보고서 길이는
`[compaction] rewind_summary_tokens`로 정하며, 기본값 1500은 horon이 직접 고른 값이다.
값은 `1..=4096`으로 잘리고 `0`은 "기본값을 쓴다"는 뜻이다.

요청:

```json
{"id": 7, "req": "rewind", "session_id": "s-1", "message_index": 12, "summarize": true}
```

되감기를 먼저 하고 보고서를 나중에 쓰므로, 요약이 실패해도 대화가 되감기 전으로 돌아가지
않는다.

| 일어난 일 | 메시지 기록 |
| --- | --- |
| 설정이 꺼져 있음 | 되감기만 하고 보고서는 붙이지 않음 |
| 보고서 작성됨 | 되감은 뒤 멈춘 지점 뒤에 숨은 `<system-reminder>` 메시지 하나를 붙임 |
| 버릴 메시지 없음 | 되감기만 함 |
| 완성 호출 실패 | 되감기만 하고 붙이지 않음. 이유는 `history` 응답의 `status_detail`과 데몬 로그에 남음 |
| 완성 호출 취소 | 되감기만 함 |

붙은 보고서는 화면에 보이는 대화록 메시지도, 되감기 대상도 아니므로 나중에 실행하는
`/rewind N`의 번호가 달라지지 않는다. `rewind_undo`는 되감기 전에 기록한 헤드를 복원하므로
보고서도 되감기가 버린 나머지와 함께 사라진다.

이 필드를 게이트하는 기능은 없다. 이 필드를 모르는 서버는 모르는 필드를 무시하고 평범한
되감기로 응답하므로, 구버전 데몬에 `summarize`를 보낸 클라이언트는 오류 대신 예전 동작을
받는다.

## 도구 인자 복구(프로토콜 1.16)

프로바이더의 JSON 작성기는 때때로 도구 인자의 타입을 틀리게 씁니다. 숫자가
들어갈 자리에 `"5000"`을, 불리언 자리에 `1`을 보내는 식입니다. 디스패처는
도구가 실행되기 전에 그것을 복구하고, 이제 그 복구를 세 가지 방법으로 볼 수
있습니다. 여기서 추가된 것은 모두 덧붙이는 변경입니다. 이전 클라이언트는 예전과
같은 요청을 보내고 예전과 같은 이벤트를 읽습니다.

### 이벤트: `tool_args_repaired`

해당 호출의 `tool_done` 바로 앞에, 복구된 호출마다 한 번 보냅니다. 이 이벤트를
모르는 클라이언트는 무시하며, 호출은 어느 쪽이든 끝까지 진행됩니다.

```json
{"ev":"tool_args_repaired","session_id":"s-1","call_id":"call-9","name":"bash",
 "original_input":{"command":"ls","timeout":"5000"},"changes":["coerced `timeout` to a number"]}
```

`original_input`은 모델이 보낸 그대로의 인자이고, `changes`는 복구를 적용한
순서대로 한 줄에 하나씩 적은 목록입니다.

### 저장되는 기록

저장된 도구 결과는 같은 두 값을 `original_input`과 `arg_repairs`로 함께
보관합니다. 복구가 필요 없었던 호출에서는 두 값을 생략하므로, 나머지 기록은
이 변경 전과 정확히 같은 바이트를 유지합니다.

### 카운터

`HORON_AGENT_PERF_COUNTERS=1`일 때 `snapshot().tool_arg_repairs`가 도구별
복구 호출 수를 셉니다.

## 저하 영수증(프로토콜 1.17)

프로바이더의 스키마 방언이 도구 목록의 일부를 표현하지 못하면 horon-agent는 요청을
보내기 전에 그 부분을 줄입니다. 이제 줄인 내용을 하나하나 기록합니다. 여기서 추가된
것은 모두 덧붙이는 변경입니다. 이전 클라이언트는 예전과 같은 요청을 보내고 예전과
같은 이벤트를 읽습니다.

### 이벤트: `degradation_receipts`

스트리밍 턴의 어시스턴트 메시지가 저장된 뒤, 그 요청이 이 세션에서 아직 보고하지
않은 손실을 냈을 때만 보냅니다. 이 이벤트를 모르는 클라이언트는 무시합니다.

```json
{"ev":"degradation_receipts","session_id":"s-1","message_id":"m-7",
 "receipts":[{"kind":"schema_keyword_dropped","tool":"bash","target":"uniqueItems"}]}
```

`kind`는 셋 중 하나입니다. `schema_keyword_dropped`는 방언 밖의 키워드나
`format:<값>`을 뺀 경우, `strict_disabled`는 도구를 `strict: false`로 보낸 경우,
`duplicate_tool_dropped`는 같은 이름의 두 번째 정의를 보내지 않은 경우입니다.
같은 (kind, tool, target)은 요청마다가 아니라 세션마다 한 번 보고하며, 데몬을
다시 시작하면 한 번 더 보고될 수 있습니다.

### 저장되는 기록

그 요청으로 추가된 어시스턴트 메시지는 같은 영수증을 `degradations`로 같은 추가
쓰기에서 함께 보관합니다. 손실이 없었던 요청의 메시지는 이 필드를 생략하므로 이
변경 전과 정확히 같은 바이트를 유지합니다.

### 거절 뒤 재시도

예방 단계는 선언된 허용 목록으로 도구 목록을 줄이므로, 목록 밖의 구성 요소는
프로바이더에 도달하지 않습니다. 그러나 허용 목록은 완전할 수 없고, 프로바이더가
그래도 거절하면 그 도구를 실은 모든 턴이 실패합니다.

직접 Chat Completions 경로는 이제 같은 턴 안에서 그 거절을 회복합니다. 본문이
스키마 키워드나 `format`을 지목한 `4xx`는 학습되고, 도구 목록은 그것을 빼고 다시
만들어지며, 요청은 한 번 더 전송됩니다. 손실은 재시도한 요청에 평범한
`schema_keyword_dropped` 영수증으로 나타나므로, 클라이언트는 이미 처리하는 같은
`degradation_receipts` 이벤트를 봅니다. 학습은 구성 요소마다 한 번으로 제한되므로,
같은 것을 다시 지목한 두 번째 거절은 재시도 대신 보고됩니다.

다이얼렉트를 배울 수 있는 것은 클라이언트 오류뿐입니다. `429`, `5xx`, `401/403`은
일시적이거나 자격증명 문제이므로 회복 단계는 그것에서 배우지도, 재시도하지도
않습니다. 따라서 공용 페일오버 분류는 이전과 같은 상태 코드를 봅니다. #713의
"schema must have a 'type' key"처럼 뺄 것이 없는 오류는 첫 실패에서 재시도가 도움이
되지 않는다는 힌트와 함께 보고됩니다.

## 메시지 전달 모드(프로토콜 1.18)

턴이 도는 중에 도착한 메시지는 세션의 대기열에 남았다가 다음 전달 지점에서 주입됩니다.
`[messages]`는 그 지점마다 몇 개를 가져갈지와, 대기 중인 메시지가 실행 중인 도구를
멈추는지를 정합니다. 여기서 추가된 것은 모두 덧붙이는 변경입니다. 이전 클라이언트는
예전과 같은 요청을 보내고 예전과 같은 이벤트를 읽습니다.

| 키 | 값 | 기본값 | 뜻 |
| --- | --- | --- | --- |
| `follow_up_mode` | `all`, `one-at-a-time` | `all` | 턴의 첫 전달 지점이 가져가는 메시지 수. 앞 턴에서 남은 메시지다 |
| `steering_mode` | `all`, `one-at-a-time` | `all` | 같은 턴의 그 뒤 전달 지점이 가져가는 메시지 수 |
| `interrupt_mode` | `wait`, `immediate` | `wait` | 대기 중인 메시지가 실행 중인 도구를 기다리는지, 남은 도구를 멈추는지 |

두 큐 모드의 기본값 `all`은 지금까지의 horon 동작을 그대로 유지합니다. 이는 omp의
기본값(`one-at-a-time`)과 일부러 다릅니다. 설정하지 않은 데몬이 예전에 함께 전달하던
메시지를 나누어 보내기 시작하면 안 되기 때문입니다. `one-at-a-time`은 남은 메시지를
순서대로 대기열에 두므로 메시지마다 따로 주입됩니다.

### 요청: `get_message_modes`

```json
{"v":1,"id":7,"req":"get_message_modes","session_id":"s-1"}
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | 문자열 | 예 | 질문의 대상 세션 |

### 응답: `message_modes`

```json
{"v":1,"reply_to":7,"ev":"message_modes","session_id":"s-1",
 "modes":{"follow_up_mode":"all","steering_mode":"one-at-a-time","interrupt_mode":"wait"}}
```

문자열은 설정 파일에 쓰는 표기 그대로이므로 클라이언트가 열거형을 다시 문자로 바꾸지
않습니다.

### 동작

세 값은 세션 상태가 아니라 데몬 설정입니다. 브리지가
`crates/harness-api-server/src/message_modes.rs`에서 데몬에 묻지 않고 직접 답하며,
지목한 세션이 있는지와 무관하게 답합니다. 클라이언트는 대화 상대인 데몬의 모드를
세션 전이나 세션 없이 읽습니다.

이 요청·응답 쌍을 게이트하는 기능은 없습니다. 추가형이므로 이 요청을 모르는 서버는
`unknown_request`로 답하고, 그 오류를 받은 클라이언트는 기본값을 가정하지 않고 모드를
알 수 없음으로 다룹니다. SDK는 이 호출을 `get_message_modes`(Rust, Python)와
`getMessageModes`(TypeScript)로 제공합니다.

텍스트 도구 호출을 재시도할 때 `soft_interrupt_injected`는 `point: "native_tool_retry"`와 화면에 표시할 선택 필드 `notice`를 보냅니다. 안내는 이어질 재시도를 설명합니다. 표시할 안내가 없는 인터럽트는 이 필드를 생략합니다.

## 도구 판정(프로토콜 1.19)

하네스 API는 주 버전 1을 유지하고 부 버전 18에서 19로 옮겼습니다. 아래 내용은 모두
추가형입니다. 새 필드를 보지 않는 클라이언트는 이전과 같은 이벤트를 읽습니다.

도구 호출은 텍스트와 오류 표시만 보고했으므로, 호출이 실행됐는지, 일부만 끝났는지,
거부됐는지 알려면 문장을 읽어야 했습니다. 저장된 `tool_result`는 이미 타입이 붙은
판정을 담고 있고, 이 버전은 같은 값을 호출을 끝내는 이벤트에도 싣습니다.

| 필드 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| `verdict` | string | 아니오 | 데몬이 판정을 저장했을 때, 그 호출이 어떻게 됐는지 |

값은 저장된 결과가 쓰는 일곱 가지 전송 표기입니다.

| 값 | 의미 |
| --- | --- |
| `ok` | 도구가 실행됐고 결과 전체를 돌려줬습니다 |
| `partial` | 도구가 실행됐지만 작업 일부만 끝났습니다 |
| `truncated` | 도구가 끝까지 실행됐고 돌려준 텍스트는 전체의 일부입니다 |
| `withheld` | 도구가 실행됐고 결과 대신 거부 문장을 돌려줬습니다 |
| `rejected` | 도구가 실행되기 전에 호출이 거부됐습니다 |
| `failed` | 도구가 실행됐고 오류를 돌려줬습니다 |
| `interrupted` | 사용자, 재적재, 취소로 호출이 건너뛰어지거나 중단됐습니다 |

어떤 계층도 호출에 판정을 남기지 않으면 필드는 없습니다. 대부분의 도구는 그냥 성공한
호출에 아무것도 남기지 않으므로, 보통의 성공한 `tool_done`에는 판정이 없고 `ok`는
도구가 직접 밝힌 경우에만 나옵니다. 백그라운드로 넘어간 호출에는 판정이 없고, 제공자가
자기 쪽에서 실행하는 도구(예: 호스팅 검색)에도 그 도구가 오류를 보고하더라도 판정이
없습니다. 모델이 낸 도구 호출에 제공자가 준 결과는 오류 표시가 붙어 있으면
`failed`입니다. 필드가 없으면 프레임은 프로토콜 1.18과 바이트 단위로 같고, 읽는 쪽은
이전처럼 `error`로 성공과 실패를 가릅니다.

### 이벤트: `tool_done`

```json
{"v":1,"ev":"tool_done","session_id":"s-1","call_id":"call-1","name":"bash",
 "output":"Error: command timed out","error":"Error: command timed out",
 "verdict":"failed"}
```

이 필드를 게이트하는 기능은 없습니다. 모든 클라이언트가 이미 읽는 이벤트에 실리므로
이전 클라이언트는 키를 무시하고, 판정을 원하는 클라이언트는 값을 읽고 없으면 `error`로
대체합니다.

## 세션 영구 삭제(프로토콜 1.20)

하네스 API는 major 버전 1을 유지하고 minor 버전이 19에서 20으로 올라갔다.
추가는 요청 하나라서, 이 요청을 보내지 않는 클라이언트는 이전과 같은 프레임을 읽는다.

`archive_session`은 세션을 숨기고 다시 열 수 있게 남긴다. 이 요청은 반대 동작이다.
대화 기록과 세션 아이디로 이름 붙은 모든 것이 디스크에서 사라지고, 되살릴 방법이 없다.

### 요청: `delete_session`

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `req` | string | 예 | `"delete_session"` |
| `session_id` | string | 예 | 지울 세션. 전체 아이디 또는 고유 접두부 |
| `confirm` | boolean | 아니오 | 거절을 가르는 와이어 필드. 브리지는 항상 `true`를 보낸다 |

```json
{"v":1,"id":12,"req":"delete_session","session_id":"s-1"}
```

응답은 `{"v":1,"reply_to":12,"ev":"ok"}`다.

### 동작

- 그 세션을 위해 턴이 돌고 있거나, 다른 프로세스가 스트리밍 중이거나, 클라이언트가 아직 붙어
  있는 세션은 오류로 거절한다. 살아 있는 라이터 밑에서 지우면 그 라이터와 경쟁하기 때문이다.
  먼저 닫거나 분리해야 한다. 데몬이 턴 사이에 들고 있는 유휴 세션은 열린 세션이 아니며,
  클라이언트가 떠난 뒤 재연결 유예로 남은 세션도 마찬가지다. 둘 다 닫은 뒤 지운다.
- `detach_session`은 `ok`를 보내기 전에 이 연결의 등록을 해제하므로, 분리 직후 보낸 삭제가
  그 연결을 붙어 있는 것으로 보지 않는다.
- 이 브리지 연결이 붙어 있는 세션도 같은 이유로 거절하며, 브리지가 왕복 전에 알려 준다.
- 없는 아이디는 `unknown_session`이고, 알 수 없는 `attach_session`과 같은 응답이다.
- 같은 아이디를 두 번째 지워도 성공하므로 반복 호출이 안전하다.
- 보관된 세션도 다른 세션과 똑같이 지운다. 아카이브와 삭제는 별개 동작이고, 어느 쪽도
  다른 쪽을 함의하지 않는다.
- 프로세스 전역 상태는 세션의 것이 아니므로 지우지 않는다. 관리 스킬, 모델, 설정, 승인 상태,
  사용량 데이터베이스가 여기 해당한다.

이 요청을 거는 캐퍼빌리티는 없다. 추가 요청이라, 이 요청을 모르는 서버는 `unknown_request`로
답하고 클라이언트는 그것을 "세션이 없다"가 아니라 "이 빌드는 삭제할 수 없다"로 읽는다. SDK는 Rust와 Python에서
`delete_session`, TypeScript에서 `deleteSession`으로 노출한다.

## Swarm 채팅 표면 제거(프로토콜 1.21)

하네스 API는 주 버전 1을 유지하고 부 버전이 20에서 21로 올라간다. 이 항목은 **표면 변경이 아니라
제거 사실의 기록**이다. 없어진 swarm 채팅 기본 연산(`swarm` 동작 `share`, `share_append`, `read`,
`channel`, `list_channels`, `channel_members`, `subscribe_channel`,
`unsubscribe_channel`과 `swarm message`의 `channel` 인자)은 내부 데몬 와이어
(`horon-agent-protocol`)와 `swarm` 도구 스키마에만 있었다. 어느 것도 하네스 API 요청·이벤트·필드로
노출된 적이 없으므로 1.20을 쓰던 클라이언트는 같은 프레임을 보내고 읽는다.

제거 사실을 여기에 적는 이유는 세션 전사에 담길 수 있는 내용과 옛 세션의 재생이 바뀌기
때문이다.

- 와이어 요청 `CommShare`, `CommRead`, `CommListChannels`, `CommChannelMembers`,
  `CommSubscribeChannel`, `CommUnsubscribeChannel`이 사라졌다. 서버 이벤트 `CommContext`,
  `CommChannels`, 알림 타입 `SharedContext`, `NotificationType::Message`의 `channel` 필드,
  `SwarmEventType::ContextUpdate`, `ContextEntry`, `SwarmChannelInfo` 타입도 함께 사라졌다.
- 제거 전에 저장된 세션은 불러오기·프로젝션·렌더를 거치면서 `swarm` 도구 호출의 이름과 인자를
  그대로 유지하므로, 재개해도 전사가 사라지지 않는다. 재생은
  `session::tests::retired_swarm_actions`가 검증한다.
- 없어진 동작을 부르는 새 호출은 브로드캐스트로 떨어지지 않고 실패한다. 도구는
  `Action '\<name>' was removed: the swarm shared-context store and topic channels are gone.
  Use action='message' (with to_session for a DM) ... and artifacts for durable data.`로
  답한다. `message`에 붙인 `channel` 인자도 같은 방식으로 거절된다. 둘 다
  `tool::communicate::tests::input_format::retired_channel_and_shared_context_actions_are_rejected`가
  검증한다.

### 이전 방법

|이전|지금|
| --- | --- |
| `swarm {action:"dm"}` / `swarm {action:"message", to_session}` | 그대로 |
| `swarm {action:"broadcast"}` / `swarm {action:"message"}` | 그대로. 보내는 쪽이 띄운 서브트리에 닿는다 |
| `swarm {action:"channel", channel, message}` | 한 에이전트면 `swarm {action:"message", to_session}`, 서브트리면 `to_session` 없이 |
| `swarm {action:"share"\|"share_append"\|"read", key, value}` | 그래프 엣지의 노드 아티팩트(`complete_node`가 타입 지정 핸드오프를 나른다), swarm 관찰은 `status`/`summary` |
| `swarm {action:"list_channels"\|"channel_members"\|"subscribe_channel"\|"unsubscribe_channel"}` | 대체 없음. 그룹 도달은 띄운 서브트리다 |
| `swarm {action:"await_members"}` | 그대로 |

데몬 와이어는 같은 바이너리 안에서만 쓰는 사설 표면이므로 폐기 기간 없이 한 번에 제거했다. 옛
swarm 프레임을 말하는 외부 생산자가 없고, 하네스 API가 그 프레임을 실어 나른 적도 없다.

## 백그라운드 실시간 출력(프로토콜 1.23)

실시간 프로세스 출력을 쓰는 클라이언트는 `hello.event_capabilities`에 `background_output_v1`을 넣습니다. 브리지는 연결된 클라이언트 중 기능을 요청한 곳에만 `background_output` 이벤트를 보냅니다. 이벤트에는 `session_id`와 작업, 표준 출력·오류 구분, 일치한 줄을 담은 제한된 길이의 `text`가 들어 있습니다. 완료 결과와 저장한 작업 출력은 기존 방식으로 받습니다.

## 취소 가능한 작업(프로토콜 1.22)

하네스 API는 주 버전 1을 유지하고 부 버전이 21에서 22로 올라간다. 아래 내용은 모두 추가형이다.
새 요청 네 개를 보내지 않는 클라이언트는 이전과 같은 프레임을 읽고, 이미 알던 이벤트는 모두
그대로 해독된다.

데몬은 이 네 가지 동작을 자기 클라이언트에게 이미 제공하고 있었다. 빠진 곳은 하네스 API였다.
SDK나 데스크톱 클라이언트는 턴과 도구 호출, 백그라운드 터미널을 시작할 수 있었지만 어느 것도
멈추지 못했고, 무엇이 아직 돌고 있는지도 물을 수 없었다. 이 버전이 그 네 동작을 소켓 위에
올리고 하나의 능력 뒤에 묶는다.

|능력|통제하는 표면|
| --- | --- |
| `cancellable_work_v1` | `cancel_turn`, `cancel_tool_call`, `cancel_background_terminal`, `list_background_work`와 아래 응답 이벤트 세 개 |

브리지는 다른 게이트 능력과 마찬가지로 `cancellable_work_v1`을 항상 광고하므로 클라이언트는
보내기 전에 확인할 수 있다. 실제로 요청이 도는지는 브리지 뒤의 데몬에 달려 있다. 데몬이 자기
능력 목록에 `cancellable_work_api`를 광고해야 한다. 광고하지 않는 데몬이면 이 프로토콜 버전에서
유효한 요청이므로 `unknown_request`가 아니라 `cancellable_work_v1`을 적은 `unsupported`로
답한다. 원인은 소켓 뒤의 빌드이기 때문이다. 브리지는 데몬이 이 네 요청을 처리할 때만 넘길 수
있고, 옛 데몬이 조용히 버릴 프레임을 쓰는 대신 거절하는 편이 낫다. 그러지 않으면 클라이언트가
자기 타임아웃까지 기다리게 된다.

### 요청

|요청|필드|뜻|
| --- | --- | --- |
| `cancel_turn` | `session_id`, `run_id` | 호출자가 시작하는 것을 본 바로 그 실행만 멈춘다 |
| `cancel_tool_call` | `session_id`, `call_id` | 턴은 계속 돌게 두고 도구 호출 하나를 멈춘다 |
| `cancel_background_terminal` | `session_id`, `call_id` | 이 세션이 띄운 백그라운드 터미널 하나를 멈춘다 |
| `list_background_work` | `session_id` | 이 세션에서 아직 돌고 있는 작업 |

`cancel`은 이미 있었고 돌고 있는 턴을 무엇이든 멈춘다. `cancel_turn`은 클라이언트가 관찰한 실행
id를 지정하므로, 이미 끝난 턴과 경쟁에서 진 취소가 다음 턴에 닿지 않는다. `run_id`와 `call_id`는
비어 있으면 안 되고, 빈 값은 아무것도 넘기기 전에 `invalid_request`로 거절된다.

취소된 도구 호출도 `tool_done`을 보고하고 취소된 턴도 자기 정지를 보고하므로 전사는 유효하게
남고 모델은 자기가 낸 모든 호출에 결과를 받는다. 백그라운드 작업의 정지는 응답이 아니라 마지막
`background_work` 이벤트가 확인한다. 응답은 취소가 접수됐다는 것만 말한다.

소켓 뒤 데몬 쪽에서는 순서 규칙이 두 가지 적용된다. 끝난 턴은 그 세션의 다음 `message`를 읽기 전에 닫히므로, 턴의 종료 이벤트에 다음 prompt로 답하는 클라이언트가 `Already processing a message`로 거절되지 않는다(`crates/app-core/src/server/client_lifecycle.rs:824-834`). 그 종료 이벤트에 `no_reply` 메시지로 답하면 그것은 문맥 메시지다. 턴을 시작하지 않으므로 끝난 턴의 완료 꼬리를 기다렸다가 정확히 한 번 저장하고 `context_message_added`로 답한다. 실제로 도는 턴, 즉 이 연결의 턴이나 어느 클라이언트든 등록한 턴만 바쁨 오류로 답하며 그 답도 곧바로 한다. 그리고 취소의 `Interrupted`와 그 턴의 `Done`은 취소한 턴 자신의 프레임이 모두 전달된 뒤에 쓰이며, 그 대기는 500ms가 상한이다(`crates/app-core/src/server/client_lifecycle.rs:4026-4036`, `crates/app-core/src/server/fanout_flush.rs:56-60`).

### 이벤트

```json
{"v":1,"reply_to":10,"ev":"cancel_turn_result","session_id":"s-1","run_id":"run-7","accepted":true}
{"v":1,"reply_to":11,"ev":"tool_call_cancel_result","session_id":"s-1","call_id":"call-3","accepted":false,"reason":"final"}
{"v":1,"reply_to":12,"ev":"background_work_list","session_id":"s-1","items":[{"call_id":"call-4","task_id":"bg_9","kind":"terminal"}]}
```

|이벤트|필드|
| --- | --- |
| `cancel_turn_result` | `session_id`, `run_id`, `accepted`, 선택 `reason` |
| `tool_call_cancel_result` | `session_id`, `call_id`, `accepted`, 선택 `reason` |
| `background_work_list` | `session_id`, `items` |

모든 응답은 자기가 답하는 `run_id`나 `call_id`를 그대로 되돌려 준다. 데몬 프레임은 요청별 상관
없이 연결로 브로드캐스트되므로, 이 반향이 없으면 취소 두 개를 동시에 보낸 클라이언트가 엉뚱한
응답을 짝지을 수 있다.

반향은 데몬이 붙이는 값이므로, 이 필드가 없던 데몬과 연결된 브리지는 그 프레임에 대해 빈 값을 담은
응답을 보내는 대신 응답을 보내지 않는다. 클라이언트는 엉뚱한 요청의 판정을 받는 대신 자기 요청의
시간 초과를 겪고, 그 실패는 원인을 짚을 수 있는 형태다.

`reason`은 취소가 접수됐으면 없고, 거절이면 이유를 적는다.

|값|뜻|
| --- | --- |
| `unknown` | 세션이 그 실행을 돌리고 있지 않거나 그 호출을 모른다 |
| `final` | 호출이 이미 끝났다 |
| `not_cancellable` | 호출은 있지만 이 요청으로 멈출 수 없다 |

`background_work_list`의 항목은 `call_id`, `task_id`, `kind`, `command`, `cwd`, `output`을
나른다. `kind`는 `terminal` 또는 `tool_call`이다. 뒤 세 필드는 해당하지 않으면 없고, `output`은
지금까지 나온 출력의 마지막 64 KiB를 base64로 담는다. 도구 호출이 시작한 작업만 나열한다. 데몬
자체 관리 작업은 호출 id도 편집기 쪽 자리도 없다.

브리지는 데몬 객체를 그대로 넘기지 않고 항목을 필드별로 다시 해독하므로, 나중 데몬이 더한 필드는
그것을 읽을 수 없는 클라이언트에 닿지 않고 버려진다.

### 클라이언트 호환성

- 세 이벤트는 새 이름이다. 그것을 모르는 클라이언트는 모르는 이벤트를 모두 건너뛰듯이 건너뛰고,
  옛 프레임의 왕복은
  `schema_snapshot_tests::older_event_frames_still_decode_after_the_enum_grew`가 검증한다.
- `cancel_turn` 응답은 `cancel`이 늘 답하던 기존 `ok` 확인 뒤에 도착하므로, 확인을 기다리는
  클라이언트는 영향을 받지 않는다.
- SDK는 네 동작을 `cancel_turn`/`cancelTurn`, `cancel_tool_call`/`cancelToolCall`,
  `cancel_background_terminal`/`cancelBackgroundTerminal`,
  `list_background_work`/`listBackgroundWork`로 노출하고, 능력이 없으면 소켓에 쓰기 전에
  거절한다.

## 실시간 할 일 갱신(프로토콜 1.24)

`hello.event_capabilities`에서 `live_todo_v1`을 요청하고 `hello_ok`에 같은 기능이 있는지 확인합니다. 데몬이 실시간 갱신을 지원해야 합니다. 할 일 변경을 저장하면 연결한 세션에 `session_id`가 담긴 `todo_changed`가 도착합니다. 이벤트에는 할 일 목록이 들어 있지 않습니다. 최초 `get_todo_state` 조회 전에 구독하고 연결 중인 세션의 변경 알림을 받으면 다시 조회합니다. 응답에는 최신 목록이 들어 있으므로 여러 알림에 한 번만 조회해도 됩니다. 기능을 요청하지 않은 클라이언트는 `todo_changed` 없이 목록을 계속 조회할 수 있습니다.

## 저장한 메시지 직전에서 세션 분기

`session_fork_at_v1`은 `fork_session_at` 요청을 허용합니다. 연결된 `session_id`와 `get_history`에서 읽은 `boundary_message_id`를 전달합니다. 데몬은 해당 사용자 메시지 직전까지의 이력으로 새 세션을 저장하고 `session_forked`를 반환합니다. 원본에는 전체 이력이 남습니다. 선택한 메시지가 현재 이력의 경계에서 사라졌으면 데몬이 요청을 거부하고 클라이언트는 원본에 계속 연결됩니다.

## 데몬 유효 설정(프로토콜 1.25)

하네스 API는 주 버전 1을 유지하고 부 버전 24에서 25로 옮겼습니다. 이 요청을 보내지 않는 클라이언트는 이전과 같은 프레임을 읽으므로 모두 추가형입니다.

클라이언트 자체 선호만 보여 주는 설정 화면으로는 턴이 왜 그렇게 동작하는지 설명할 수 없습니다. `get_effective_settings`는 **고정 허용 목록**에 있는 데몬 값과 그 값을 공급한 계층을 보고합니다. 전부 덤프가 아니라 목록입니다. 다른 키를 담는 필드도, 원본 파일 텍스트도 없으므로 설정 파일에 자격 증명이 들어 있어도 어떤 형태로든 클라이언트에 닿지 않습니다. `effective_settings_v1`이 이 쌍을 게이트합니다.

### 요청: `get_effective_settings`

```json
{"v":1,"id":7,"req":"get_effective_settings","session_id":"s-1"}
```

| 필드 | 형식 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | 문자열 | 예 | 질문 대상 세션 |

### 응답: `effective_settings`

```json
{"v":1,"reply_to":7,"ev":"effective_settings","session_id":"s-1",
 "settings":[{"key":"provider.stream_idle_timeout_secs",
              "label":"Stream idle timeout (seconds)",
              "value":"240","source":"file","origin":"/home/u/.horon/config.toml"}]}
```

| 필드 | 형식 | 뜻 |
| --- | --- | --- |
| `key` | 문자열 | 설정 경로. 예: `provider.stream_idle_timeout_secs` |
| `label` | 문자열 | 행에 보일 사람이 읽는 이름 |
| `value` | 문자열 | 유효 값. 화면이 인쇄하는 그대로 |
| `source` | `default`, `cli`, `file`, `env` | 값을 공급한 계층 |
| `origin` | 문자열, `default`면 없음 | `source`가 가리키는 플래그, 파일 경로, 변수 이름 |

`value`가 문자열인 이유는 화면이 그대로 인쇄하기 때문입니다. 클라이언트가 숫자를 직접 렌더링하면 어느 키가 숫자인지 알아야 하고, 그 지식은 모든 클라이언트가 아니라 허용 목록 옆에 있어야 합니다.

### 허용 목록

행은 `provider.openai_reasoning_effort`, `provider.anthropic_reasoning_effort`, `provider.stream_idle_timeout_secs`, `provider.max_retries`, `tools.profile`, `tools.mcp_tools`, `tools.approval_mode`, `tools.ask_policy`, `tools.secrets_mode`, `compaction.mode`, `messages.{follow_up,steering,interrupt}_mode`입니다. 데몬의 표에 키를 넣는 것만이 행을 만드는 방법이고, 그 밖의 값은 보고될 수 없습니다.

### 동작

답하는 쪽은 **데몬**입니다. 데몬이 실제로 불러온 설정으로 답합니다. 세션이 실제로 도는 프로세스는 데몬이고, 그 프로세스의 환경, 실행 플래그, 설정 파일이 곧 유효 값과 출처입니다. 브리지는 번역만 합니다. 내부 프로토콜로 `get_effective_settings`를 전달하고 돌아온 행을 그대로 넘깁니다. 표와 출처 판정은 `crates/base/src/effective_settings.rs`에 있고, `crates/app-core/src/server/effective_settings.rs`가 그 행을 이 응답으로 옮깁니다.

데몬은 ping에서 `effective_settings_api`를 광고합니다. 브리지는 `effective_settings_v1`을 항상 광고하고, 뒤에 있는 데몬이 그 요청을 광고하지 않으면 그 기능 이름을 담은 구조화된 `unsupported`로 거부합니다. 옛 데몬은 모르는 요청에 id 없는 프레임으로 답하므로, 그대로 전달하면 클라이언트가 자기 타임아웃만큼 기다리게 됩니다. 옛 브리지(기능 자체를 광고하지 않음)와 옛 데몬(이름을 붙여 거부됨)은 클라이언트에게 같은 "이 데몬은 설정을 보고하지 않는다" 상태로 보입니다.

계층은 근거가 강한 순서로 정합니다.

1. `cli` — 실행기가 기록한 플래그입니다. 실행기는 `--tool-profile`, `--mcp-tools` 같은 플래그를 환경 변수로 바꾸므로, 환경만 보아서는 플래그와 사용자가 내보낸 변수를 구분할 수 없습니다. 아무것도 선택하지 않아 실행기가 고른 기본값은 아예 보고하지 않습니다. 변수는 존재하지만 사용자가 설정한 것이 아닙니다.
2. `env` — 이 프로세스가 읽었고 데몬이 적용하는 변수입니다. 데몬이 무시하는 변수(0인 타임아웃, 파싱되지 않는 재시도 횟수, 모르는 모드)는 유효 값의 출처로 보고하지 않습니다.
3. `file` — 유효 설정 파일입니다. 데몬이 하는 것과 같은 엄격한 파싱으로 한 번에 읽은 문서이고, 파일이 선언한 값이 데몬이 적용하는 값이며 유효 값과 같을 때만 출처가 됩니다. 파싱되지 않는 파일은 아무것도 공급하지 않았으므로 그 행은 `default`로 읽힙니다. 데몬이 거부하는 형식의 값도 마찬가지입니다. 예를 들어 `approval_mode = "nonsense"`는 기본값으로 떨어지고, 파일은 그 기본값의 출처가 되지 않습니다.
4. `default` — 함께 배포된 값입니다.

행은 데몬 자체 설정을 설명합니다. 세션이 실행 중에 자기 값만 바꾼 경우(예: `set_session_approval_mode`)는 여기에 반영되지 않습니다. 이 행은 데몬이 불러온 값을 보고하고, 한 세션이 나중에 덮어쓴 값은 보고하지 않습니다.

쓰기는 없습니다. 요청은 구조상 읽기 전용이고, 읽지 못하는 클라이언트는 데몬 기본값으로 계속 동작합니다. SDK는 이 호출을 `get_effective_settings`(Rust, Python)와 `getEffectiveSettings`(TypeScript)로 노출하고, 기능이 광고되지 않았으면 보내기 전에 거부합니다. TUI의 `Daemon` 탭이 배포되는 소비자입니다.

## 세션 이벤트 저장소와 복제(프로토콜 1.12)

하네스 API는 주 버전 1을 유지하고 부 버전 11에서 12로 옮겼다. 아래 내용은 모두
추가형이다. 이미 보내던 요청만 보내는 클라이언트는 계속 동작하고, 대화 기록을 읽는
데 새 요청이 필요하지 않다.

클라이언트는 핸드셰이크를 협상하고 무엇이든 보내기 전에 필요한 기능을 확인한다.
브리지는 기존 집합에 더해 다음을 광고한다.

| 기능 | 통제 대상 |
| --- | --- |
| `session_event_store_v1` | `list_session_heads`, `select_session_head` |
| `session_replication_v1` | `export_session_events`, `import_session_events`, `export_session_blob`, `import_session_blob`, `get_session_blob_status`, 그리고 전체 레코드 blob 쌍 |
| `session_history_cursor_v1` | `get_history_page` |
| `structured_compaction_v1` | `compacted` 레코드의 구조화 요약 필드 읽기. 이 기능으로 통제되는 메서드는 없다 |

기능 없이 보낸 요청은 빠진 기능 이름을 담아 `unsupported`로 응답한다. 이는 버전
오류가 아니다. 데몬과 브리지를 모두 갱신해 재시작하거나, 이 빌드에 대해 그 메서드를
쓰지 않아야 한다.

### 헤드

세션은 분기된 가져오기 뒤에, 또는 되감은 브랜치에 턴이 덧붙은 뒤에 헤드를 여러 개
보유한다. 되감기만으로는 헤드가 늘지 않는다. 되감기는 이벤트를 쓰지 않고 이미 있는
그래프 위에 선택만 기록하므로 로그의 끝은 하나로 남는다. 선택된 헤드는
**호스트 로컬**이다. 복제되지 않고 세션의 영구 정체성에도 속하지 않는다.
`list_session_heads`는 헤드와 현재 선택을 보고하며, 여러 헤드 중 명시적 선택이
필요하면 `selected_head`가 없다. 하나를 선택할 때까지 실행을 거부하고, 다른
프로세스가 쓰기 권한을 쥐고 있으면 `select_session_head`가 `busy`로 응답한다.
클라이언트는 사용자의 다음 턴이 무엇에서 이어지는지를 바꾸므로, 몰래 하나를
고르지 말고 그 선택을 사용자에게 보여 줘야 한다.

### 기록

`get_history`는 바뀌지 않았고 여전히 보이는 전체 대화 기록을 돌려준다. 기록 행의 `content`는 예전 값 그대로이고, 저장된 어시스턴트 행이 추론 추적을 함께 담으면 보이는 텍스트 블록만 이어 붙인 `answer` 필드를 덧붙인다. 답 자체가 필요한 클라이언트는 데몬의 추론 마크업을 해석하지 않아도 된다. 추론이 없는 행에는 이 필드가 없다. 행에는 그 행을 렌더링한 저장 메시지의 id인 `message_id`도 붙을 수 있다. 다리가 데몬에 이 id를 요청하므로 이 값을 알려 주는 데몬의 행에는 있고, 합성된 행과 이 값을 모르는 구형 데몬의 행에는 없다.
`get_history_page`는 긴 세션에서 UI가 원하는 제한 읽기다. `session_id`, 선택적
`head_event_id`(기본값은 선택된 헤드), 불투명 이어가기 값 `before_event_id`,
`limit`(기본 50, 최대 200)을 받는다. 응답은 고정된 `head`, 페이지 메시지를 오래된
것부터 담은 목록, `before_event_id`로 되돌려 넘길 `next_cursor`를 가진
`SessionHistoryPage`다. 사용자가 스크롤하는 동안 `head_event_id`를 고정한다. 헤드를
고정한 커서는 선택이 바뀐 뒤에도 같은 기록을 가리킨다.

### 복제

`export_session_events`는 고정 헤드에 대한 원본을 부모 우선으로 한 페이지씩 제한해
돌려준다. `import_session_events`는 커밋 전에 페이지 전체를 검증하고
`accepted_ids`, `heads`, `retry_cursor`, `conflict_heads`로 응답한다. 원본 blob은
1 MiB 청크로 따로 이동하며 발행 전에 SHA-256과 크기로 검증한다. 중단된 전송은
`get_session_blob_status`에서 이어 간다.

### Markdown 대화록

`export_session_markdown`은 `session_id`를 받아 읽을 수 있는 대화록 전체를
`markdown`에 담은 `session_markdown` 이벤트로 응답한다. 각 턴은 `### User` 또는
`### Assistant` 제목과 그 내용으로 이루어진다. 텍스트는 그대로, 도구 호출은 JSON
코드 블록으로, 도구 결과는 코드 블록으로, 이미지와 오디오 블록은 짧은 자리표시자로
표시한다. 비밀 값은 디스크 경로가 쓰는 같은 패턴 표로 가리므로, 이벤트 로그에
들어가지 않은 토큰은 대화록에도 나타날 수 없다. 4 KiB를 넘는 도구 결과는 UTF-8
경계에서 잘리고 `… (truncated, N bytes total)` 표시로 바뀐다.

이 응답은 복제 프로토콜에 속하지 않으므로 `protocol_version`이 필요 없다.
다른 저장 세션 읽기를 이미 막는 `session_replication_v1` 기능을 요구한다. 없는
세션에는 다른 읽기와 같은 `unknown_session` 오류로 답한다.
`horon export <session-id> [--out <path>]`는 두 경로가 같은 렌더러를 쓰므로
같은 바이트를 쓴다.

클라이언트가 어겨서는 안 되는 규칙 두 가지:

- **`canonical_json`을 다시 직렬화하지 않는다.** 이벤트의 정규 JSON은 문자열로
  이동한다. 2^53을 넘는 `u64`, `1.0`, `-0.0`이 JavaScript 숫자 왕복을 견디지
  못하기 때문이다. 문자열을 그대로 통과시킨다.
- **`conflict_heads`를 데이터로 다룬다.** 분기된 헤드는 모두 보존된다. 타임스탬프로
  승자를 정하지 않으며, 가져오기는 사용자가 고르지 않은 분기를 버리면 안 된다.

가져오기를 다시 보내는 것은 안전하다. 같은 ID에 같은 해시면 아무 일도 일어나지
않는다.

### 오류

안정된 `ErrorCode` 값 다섯 개는 바뀌지 않았으므로 구버전 클라이언트도 계속 해독한다.
더 자세한 원인은 선택적 `details` 객체로 온다. `store_code`(예: `hash_conflict`,
`missing_dependency`, `conflict_heads`, `busy`, `invalid_cursor`,
`record_too_large`), `retryable`, `accepted_ids`, `retry_cursor`,
`conflict_heads`가 여기에 들어간다. `details`를 쓰지 않으면 무시한다. 재시도 전에
`retryable`로 분기하고, `hash_conflict`는 바꾸지 않은 채 절대 재시도하지 않는다.

### 상태

`runtime_info`는 현재 호스트 런타임에서 생존 여부를 구성한다. 오래된 세션
메타데이터에 기록된 PID는 과거 보조 정보일 뿐 살아 있는 프로세스가 아니며, 어떤
클라이언트도 이를 실행 중으로 표시하면 안 된다.

### 런타임 식별 필드

`get_runtime_info`는 세션의 식별 정보를 답한다. 그중 두 필드는 한 턴을 답한 모델이
세션이 고른 모델과 항상 같지는 않다는 사실 때문에 있다.

| 필드 | 타입 | 의미 |
|---|---|---|
| `fallback_models` | `array<string>` | 활성 이름 지정 공급자 프로필에 설정된 폴백 모델 ID이며, 한 턴이 시도하는 순서다. 목록이 비어 있으면 키 자체가 없다. |
| `serving_model` | `string` | 가장 최근 어시스턴트 응답을 만든 모델이다. 폴백이 답한 뒤에는 세션 자체 선택으로 돌아간 `model`과 값이 다르다. 아직 지목할 응답이 없으면 없다. |

두 필드 모두 선택적이다. 구버전 데몬은 이 필드를 생략하고, 이를 무시하는
클라이언트는 계속 동작한다. 카탈로그와 식별 정보를 한 번 받은 뒤에는, 예비 모델 목록이
없을 때 브리지가 `get_runtime_info`에 캐시로 답한다. 이때 응답한 모델은 세션의 모델뿐이기
때문이다. 예비 모델 목록이 있거나 식별 정보를 아직 받지 못했으면 매 `get_runtime_info`마다
데몬에 카탈로그를 묻는다. 카탈로그가 바뀌지 않아도 응답한 모델이 바뀔 수 있기 때문이다.

### 클라이언트가 떠난 뒤의 연결 수명

브리지는 클라이언트 소켓이 열려 있는 동안 API 연결을 서비스하고, 그 클라이언트를
위한 데몬 연결을 하나 쥔다. 클라이언트가 사라지면 브리지는 데몬 쪽 연결을 닫고
소켓에서 계속 기다린다. 바인드에 실패했거나 리스너를 잃은 브리지만 종료한다.

이 규칙의 클라이언트 쪽은 시험 환경에서 틀리기 쉽다. 소켓을 읽기와 쓰기 반쪽으로
나눠도 각 반쪽이 독립된 연결이 되지는 않으므로, 쓰기 반쪽만 버리면 스트림이 열린
채로 남아 브리지에 FIN이 닿지 않고 브리지는 데몬 연결을 계속 쥔다. 두 반쪽을 모두
버려야 한다. 이것은 브리지 결함이 아니라 시험 환경의 실수이며,
`crates/harness-api-server/tests/v1_client_round_trip.rs`가 두 반쪽을 모두 버리고
데몬 쪽 읽기에 시간 한도를 두는 이유다. 클라이언트가 떠난 뒤에도 데몬 연결을
쥐는 브리지는 이제 러너 타임아웃까지 멈추는 대신 단정에서 실패한다.

전체 저장 형식, 한도, 레거시 마이그레이션 규칙은
`docs/protocol/SESSION_STORE.ko.md`에 있다.

## 핸드셰이크에서 클라이언트가 알리는 질문 처리

`ask` 도구는 사람에게 질문을 보여 주고 답을 기다린다. 데몬은 화면을 그리지 않고 클라이언트가 붙어 있다고 가정할 수도 없으므로, 질문은 보여 줄 수 있다고 알린 연결로만 간다. 그 광고는 `Hello`의 불리언 필드 하나다.

| 필드 | 타입 | 없을 때 | 뜻 |
| --- | --- | --- | --- |
| `supports_ask_requests` | 불리언 | `false` | 이 연결이 `ask` 도구의 질문을 그리고 답한다 |

브리지는 이 필드를 `hello["supports_ask_requests"].as_bool().unwrap_or(false)`로 읽으므로(`crates/harness-api-server/src/lib.rs`), 이 필드가 없던 클라이언트는 아무것도 알리지 않은 채로 계속 동작한다. 이 필드는 능력 문자열도 프로토콜 마이너 협상도 아니다. 사람에게 묻는 방향을 정할 뿐이다. 붙어 있는 연결이 이 필드를 알린 세션은 그 연결에서 질문을 받고 호출이 답을 기다리며, 그런 연결이 없는 세션은 `ask_policy`로 넘어간다(`docs/safety/SAFETY.md`).

SDK 셋은 이 값을 연결 옵션 하나로 내주고, 모두 기본값을 끔으로 둔다.

| SDK | 옵션 | 기본값 |
| --- | --- | --- |
| Rust | `ConnectOptions::supports_ask_requests` | `false` |
| TypeScript | `supportsAskRequests` | `false` |
| Python | `supports_ask_requests` | `False` |

Rust SDK는 이 옵션을 `Hello`로 옮기고(`crates/agent-sdk/src/client.rs`), TypeScript는 `options.supportsAskRequests ?? false`를 쓰며, Python은 필드를 그대로 넘긴다. TUI 바이너리 `horon-tui`는 질문을 그리고 답하므로 `connect_options`에서 이 값을 `true`로 둔다(`crates/tui/src/lib.rs`). 턴만 돌리는 클라이언트는 기본값을 그대로 두고, `ask`에 닿은 턴은 아무도 볼 수 없는 질문에 멈춰 서는 대신 정책으로 결론 난다.

## 하네스 API 요청·이벤트 표면: usage_report, search_sessions, list_artifacts, durable_runtime

이 문서는 하네스 API에서 추가된 요청 표면을 적습니다. 앞부분은 프로토콜 1.13의 세 요청과 그 응답 이벤트이고, 그다음은 1.14의 내구 런타임 표면 넷이고, 마지막은 1.16의 인자 복구입니다. 필드 이름과 타입은 `crates/harness-api/src/requests.rs`와 `crates/harness-api/src/events.rs`의 정의를 그대로 옮겼고, 동작과 한도는 `crates/harness-api-server/src/translate/`의 구현에서 확인한 값입니다.

세 요청 모두 추가형입니다. 이 요청들을 보내지 않는 클라이언트는 계속 동작하고, 브리지는 `hello_ok`의 `capabilities`에 `usage_report`, `session_search`, `artifacts`를 광고합니다(`crates/harness-api-server/src/lib.rs`의 `BRIDGE_CAPABILITIES`).

`approval_ack`과 `failover_ack`은 `list_artifacts` 다음에 옵니다. 둘 다 클라이언트가 내구 승인이나 전환 알림을 정리하려고 보내는 ack이므로 자체 능력 뒤에 있지 않습니다. ack 태그를 모르는 데몬은 그 요청을 무시하지 않고 오류로 답합니다.

### 공통 규칙

- 프레임 하나는 JSON 객체 하나, 한 줄입니다(NDJSON). 요청은 `req`로 종류를 구분하고 `id`를 싣고, 응답은 `reply_to`로 그 `id`를 되돌려 줍니다.
- 요청 본문은 `#[serde(tag = "req", rename_all = "snake_case")]`로 직렬화되므로 필드 이름은 snake_case입니다.
- 모르는 필드는 무시하고, 모르는 이벤트 종류는 건너뜁니다.
- 실패는 `{"ev":"error","code":...,"message":...}`로 옵니다. 이 표면들이 쓰는 `ErrorCode` 값은 `invalid_request`, `unknown_session`, `internal`입니다.
- 세션을 지목하는 요청은 `session_id`를 받습니다. 없는 세션은 빈 결과가 아니라 `unknown_session`으로 답합니다. "이 세션은 아무것도 쓰지 않았다"와 "그런 세션이 없다"는 다른 사실이기 때문입니다.
- `session_id`는 6자 이상인 앞부분 일부도 받습니다. 온전한 id가 항상 이기고, 연결이 이미 아는 id는 다시 해석하지 않습니다. 여러 세션이 공유하는 앞부분은 `details.accepted_ids`에 최대 10개의 후보를 담고 `details.store_code`를 `ambiguous_session`으로 둔 `unknown_session`으로 답합니다. 오류 코드 자체는 `unknown_session`으로 남아 이전 빌드의 클라이언트도 응답을 해석합니다. 아무 세션도 해당하지 않는 앞부분은 그대로 `unknown_session`으로 답합니다.

### usage_report

첨부된 세션과 저장된 모든 세션의 토큰 사용량, 컨텍스트 창, 모델별 집계를 돌려줍니다. 한도 필드(`limits`)는 남아 있지만 이 빌드에는 그 출처가 없어 항상 빈 배열입니다. 능력 이름은 `usage_report`입니다.

#### 요청

```json
{ "v": 1, "id": 7, "req": "usage_report", "session_id": "session_..." }
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | string | 아니요 | 이 세션으로 보고를 좁힙니다. 생략하면 저장된 모든 세션과 첨부된 세션을 함께 보고합니다 |

없는 `session_id`는 `unknown_session`입니다.

#### 응답: `usage_report`

```json
{
  "v": 1,
  "reply_to": 7,
  "ev": "usage_report",
  "session_id": "session_...",
  "sessions": [],
  "totals": {},
  "models": [],
  "context_window": 200000,
  "limits": [],
  "pricing": "unknown",
  "estimated_cost": null
}
```

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `session_id` | string, 없을 수 있음 | 보고를 좁힌 세션. 전체 보고에는 없습니다 |
| `sessions` | `UsageSession[]` | 범위 안의 세션마다 한 행, 세션 id 순 |
| `totals` | `UsageTotals` | `sessions` 전체의 합 |
| `models` | `UsageModel[]` | 모델별 집계, 모델 id 순 |
| `context_window` | number, 없을 수 있음 | 첨부된 세션의 활성 경로 컨텍스트 창(토큰). 없으면 "모른다"이고 다른 모델의 기본 창이 아닙니다 |
| `limits` | `UsageLimitInfo[]` | 한도 목록. 이 빌드는 한도를 알리는 계정 출처가 없으므로 항상 빈 배열 |
| `pricing` | string | 항상 `"unknown"`. 이 저장소에는 가격표가 없습니다 |
| `estimated_cost` | number, 없을 수 있음 | 항상 `null`. 가격표가 없으니 비용 추정도 없습니다 |

`UsageSession`:

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `session_id` | string | 세션 id |
| `model` | string, 없을 수 있음 | 세션 메타데이터가 기록한 모델 |
| `input` | number, 없을 수 있음 | 입력 토큰 합. 기록한 요청이 없으면 없음 |
| `output` | number, 없을 수 있음 | 출력 토큰 합 |
| `cache_read_input` | number, 없을 수 있음 | 캐시 읽기 입력 토큰 합 |
| `cache_creation_input` | number, 없을 수 있음 | 캐시 쓰기 입력 토큰 합 |
| `requests` | number | 사용량을 기록한 제공자 요청 수. 사용자 턴 수가 아닙니다. 한 턴이 여러 요청을 내고 도구 왕복이 따로 셉니다 |

`UsageTotals`는 `input`, `output`, `cache_read_input`, `cache_creation_input`(각각 없을 수 있음), `requests`, `sessions`(합이 덮는 세션 수, 사용량이 없는 세션 포함)를 가집니다.

`UsageModel`은 `model`(메타데이터가 모델을 밝히지 않은 세션은 `unknown`), 위 네 토큰 합, `requests`, `sessions`를 가집니다.

`UsageLimitInfo`는 `name`, `used`, `limit`, `unit`(예: `usd`), `resets_at`(RFC 3339)을 가집니다. `used`, `limit`, `resets_at`은 데몬이 알렸을 때만 있습니다.

#### 동작

보고는 세 출처를 권위 순으로 합칩니다. 첨부된 세션의 데몬 누적치, 저장된 세션 원본의 `token_usage` 기록, 마지막 실시간 `token_usage` 이벤트입니다. 어떤 요청도 기록하지 않은 지표는 `0`이 아니라 `null`입니다. 제공자가 캐시 토큰을 보고하지 않은 것과 0을 보고한 것은 다른 사실이기 때문입니다.

이 빌드에는 계정 구독이 없으므로 데몬은 한도를 알리지 않고 `limits`는 항상 빈 배열입니다. 빈 배열은 "이 계정에 한도가 없다"가 아니라 "이 빌드에 한도 출처가 없다"는 뜻입니다.

세 SDK는 Rust에서 `usage_report(session_id: Option<&str>)`로 보내며 `UsageReport`를 돌려주고, TypeScript에서는 `usageReport`, Python에서는 `usage_report`입니다.

### search_sessions

첨부된 세션이 아니라 저장된 모든 세션의 트랜스크립트를 검색합니다. 능력 이름은 `session_search`입니다. 세션 전환기가 붙은 세션만 거르면 "그 대화가 어디 있었더라"에 답할 수 없기 때문에 필요합니다.

#### 요청

```json
{ "v": 1, "id": 8, "req": "search_sessions", "query": "zanzibar", "limit": 10 }
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `query` | string | 예 | 검색어. 공백만 있으면 `invalid_request`입니다 |
| `limit` | number | 아니요 | 최대 적중 수. 기본 20, 상한 50 |

`query`는 경로·glob·SQL 조각으로 해석하지 않습니다. 문자열 그대로 검색합니다. `limit`이 0이면 빈 결과를 돌려줍니다.

#### 응답: `session_search_results`

```json
{
  "v": 1,
  "reply_to": 8,
  "ev": "session_search_results",
  "query": "zanzibar",
  "results": []
}
```

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `query` | string | 요청의 검색어를 그대로 되돌려 줍니다. 검색을 여러 번 보낸 클라이언트가 화면에 남은 답을 구분할 수 있게 하려는 것입니다 |
| `results` | `SessionSearchHit[]` | 적중 목록 |

`SessionSearchHit`:

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `session_id` | string | 적중이 속한 저장 세션 |
| `title` | string, 없을 수 있음 | 그 세션의 표시 제목 |
| `role` | string | `user`, `assistant`, 또는 제목·세션 수준 적중이면 `metadata` |
| `preview` | string | 일치 지점 앞뒤를 잘라낸 평문 발췌. 잘린 구간은 `...`로 표시합니다 |
| `at` | string | 일치한 메시지의 RFC 3339 시각. 메타데이터 적중이면 세션 시각 |

#### 동작

에이전트 자신의 세션 검색과 같은 엔진, 같은 인덱스, 같은 점수를 씁니다. 그래서 에이전트에서 검색한 결과와 클라이언트에서 검색한 결과가 같습니다. 저장 디렉터리가 없으면 빈 결과이고, 엔진이 실패하면 `internal`입니다.

세 SDK는 Rust에서 `search_sessions(query, limit: Option<u32>)`, TypeScript에서 `searchSessions`, Python에서 `search_sessions`로 보냅니다.

### list_artifacts

대화가 만든 파일, 즉 대화가 실어 온 이미지와 세션이 시작된 뒤 작업 디렉터리에 쓰인 HTML·이미지 파일을 나열합니다. 능력 이름은 `artifacts`입니다.

#### 요청

```json
{ "v": 1, "id": 9, "req": "list_artifacts", "session_id": "session_..." }
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | string | 예 | 나열할 세션. 없거나 저장 기록이 없으면 `unknown_session`입니다 |

#### 응답: `artifacts`

```json
{
  "v": 1,
  "reply_to": 9,
  "ev": "artifacts",
  "session_id": "session_...",
  "artifacts": []
}
```

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `session_id` | string | 요청한 세션 |
| `artifacts` | `ArtifactEntry[]` | 최신 순 목록 |

`ArtifactEntry`:

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `path` | string | 세션 작업 디렉터리 기준 상대 경로. `/` 구분자입니다 |
| `kind` | string | `html` 또는 `image` |
| `bytes` | number | 응답 시점의 파일 크기 |
| `mtime_ms` | number | 마지막 수정 시각, epoch 밀리초 |

#### 동작

메타데이터만 돌려줍니다. 바이트는 클라이언트가 `read_file`로 따로 읽습니다. 그래서 40MB짜리 HTML 보고서도 후보마다 `stat` 한 번이면 됩니다.

목록은 두 경로에서 모읍니다. 트랜스크립트가 지목한 경로와 작업 디렉터리 스캔입니다. 두 경로 모두 세션 루트 밖으로 나가는 경로와 심볼릭 링크를 거부하므로, 트랜스크립트가 `../../.ssh/id_rsa`를 지목해도 목록에 오르지 않습니다. 세션 시작 시각을 기록이 없으면 세션 파일의 수정 시각으로 대신하고, 그보다 오래된 파일은 제외합니다. 결과는 `mtime_ms` 내림차순, 같은 시각이면 경로 오름차순으로 정렬하고 200개에서 자릅니다.

세 SDK는 Rust에서 `list_artifacts(session_id)`, TypeScript에서 `listArtifacts`, Python에서 `list_artifacts`로 보냅니다.

### approval_ack

`approval_resolved` 이벤트의 내구 사본을 정리해, 나중에 붙거나 재시작할 때 다시 보내지 않게 합니다. 승인은 ack 전까지 남습니다. 이것은 클라이언트가 보내는 ack이고 서버가 시작하는 표면이 아니므로, 응답은 `ok` 하나이고 그 뒤에 이벤트는 오지 않습니다. 이벤트 어휘의 `approval_ack`은 이 클라이언트 확인 응답에 붙은 이름이고, 데몬은 그 이벤트를 보내지 않습니다.

#### 요청

```json
{ "v": 1, "id": 21, "req": "approval_ack", "session_id": "session_...", "request_id": "req_..." }
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | string | 예 | 승인이 속한 세션. 연결이 그 세션에 붙어 있어야 합니다 |
| `request_id` | string | 예 | `approval_resolved` 이벤트의 `request_id` |

브리지가 넘기는 레거시 ack 프레임에는 세션 필드가 없으므로, 붙어 있는 연결에서 `session_id`를 빼거나 비우면 ack은 붙어 있는 세션에 적용됩니다.

#### 응답

```json
{ "v": 1, "reply_to": 21, "ev": "ok" }
```

#### 동작

- 연결이 세션에 붙어 있어야 합니다. 붙으려 한 적이 없는 연결이나 붙어 있는 세션과 다른 `session_id`를 보낸 연결은 `unknown_session`입니다. 이 검사가 필드 검사보다 먼저이므로, 붙지 않은 연결이 빈 `request_id`를 보내면 `invalid_request`가 아니라 `unknown_session`입니다.
- `request_id`가 비었거나 없으면 `invalid_request`입니다. 식별자 없는 ack은 아무것도 지우지 않으면서 성공을 보고하기 때문입니다.
- 이미 레코드가 없는 `request_id`도 `ok`로 답합니다. 러너가 먼저 레코드를 지우고 ack이 늦게 도착할 수 있으므로 늦은 ack은 실패가 아닙니다.
- 세 SDK는 Rust에서 `ack_approval(session_id, request_id)`로 보내고 `()`를 돌려주며, TypeScript에서는 `ackApproval`, Python에서는 `ack_approval`로 보내 `ok`를 기다린 뒤 보낸 값으로 만든 영수증을 돌려줍니다.

### failover_ack

`failover_switched` 알림을 그대로 되받아 데몬이 지울 수 있게 합니다. 일부만 보내면 아무것도 지우지 못하거나 다른 전환으로 읽히므로, 알림 키 전체가 함께 갑니다.

#### 요청

```json
{ "v": 1, "id": 22, "req": "failover_ack", "session_id": "session_...", "chain_id": "chain_...", "from": "model-a", "to": "model-b", "attempt": 1 }
```

| 필드 | 타입 | 필수 | 뜻 |
| --- | --- | --- | --- |
| `session_id` | string | 예 | 알림이 속한 세션. 연결이 그 세션에 붙어 있어야 합니다 |
| `chain_id` | string | 예 | 알림이 속한 전환 체인. 비어 있으면 안 됩니다 |
| `from` | string | 예 | 그 체인이 벗어난 모델. 비어 있으면 안 됩니다 |
| `to` | string | 예 | 그 체인이 옮겨 간 모델. 비어 있으면 안 됩니다 |
| `attempt` | number | 예 | 이 전환의 시도 번호. 음이 아닌 정수입니다 |

#### 응답

```json
{ "v": 1, "reply_to": 22, "ev": "ok" }
```

#### 동작

- 연결이 세션에 붙어 있어야 하며, `unknown_session` 응답과 필드 검사보다 앞선 순서는 `approval_ack`과 같습니다.
- `chain_id`, `from`, `to`가 비었거나 없으면 `invalid_request`입니다. `attempt`가 없거나 음이 아닌 정수가 아니어도 `invalid_request`입니다.
- 데몬이 그런 알림을 들고 있지 않은 키도 `ok`로 답합니다. 한 부분이라도 다른 키는 아무것도 지우지 않으므로, 클라이언트가 다섯 값을 모두 되돌려 보냅니다.
- 세 SDK는 Rust에서 `ack_failover(session_id, chain_id, from, to, attempt)`로 보내고 `()`를 돌려주며, TypeScript에서는 `ackFailover`, Python에서는 `ack_failover`로 보내 `ok`를 기다린 뒤 보낸 값으로 만든 영수증을 돌려줍니다. Python 인자 이름은 `from`이 키워드라 `from_`이고, 전선 키는 `from`입니다.

### durable_runtime_v1 · monitor_v1 · snapshot_marker_v1 · ask_receipts_v1

프로토콜 minor 14가 추가한 네 표면입니다. 넷 다 **추가형**이라, 능력을 협상하지 않은 클라이언트는
이 요청을 보내지도 받지도 않습니다. 기존 클라이언트의 동작은 바뀌지 않습니다.

| 능력 | 여는 요청·이벤트 | 무엇을 보장하는가 |
| --- | --- | --- |
| `durable_runtime_v1` | `get_runtime_state`, `apply_control`, `get_control_receipt` | 재시작 뒤에도 남는 실행 상태와, 같은 operation id의 재전송이 한 번만 집행되는 제어 영수증 |
| `monitor_v1` | 도구 `monitor`의 파일·명령 감시 | 재시작 뒤 `needs_rearm`으로 남고 명령을 다시 실행하지 않음 |
| `snapshot_marker_v1` | `get_snapshot` | `SnapshotMarker`가 `Snapshot` 바로 앞에 1:1로 오고, 그 뒤 라이브 이벤트의 `seq`가 이어짐 |
| `ask_receipts_v1` | `ask_response`의 `answer_id` | 같은 `question_id`+`answer_id`+`digest`는 저장된 결과를 재생하고, 다른 digest는 충돌 |

#### 경계 규칙

- `SnapshotMarker`와 `Snapshot`은 다른 연결로 갈 수 없습니다. 마커를 받은 연결만 스냅샷을 받습니다.
- 스냅샷 이후의 라이브 이벤트는 관측 소유자가 발급한 `seq`를 싣습니다. 클라이언트는 "N 이후는 새것"을
  스스로 증명할 수 있고, 순서를 추측하지 않습니다.
- `apply_control`은 지문을 서버가 만듭니다. 같은 id·같은 지문은 저장된 결과 재생, 같은 id·다른 지문은
  `conflict`, 동시 applying은 `pending`이며 두 번째 실행은 하지 않습니다. 재시작에서 applying으로
  남은 것은 `indeterminate`로 봉인하고 다시 실행하지 않습니다.
- 보존 범위를 벗어난 operation id는 `unknown`입니다. SDK는 그 경우 자동 재시도하지 않습니다.
- 지원 동작은 `abort_run(expected_run_id)`와 `cancel_inputs(input_ids)` 둘뿐입니다. 모델 변경·파일·셸·
  임의 명령은 이 표면에 없습니다.
- 브리지가 광고하지 않는 능력에 걸린 요청은 도달할 수 없습니다. 그래서 네 문자열이 모두
  `BRIDGE_CAPABILITIES`에 있습니다.
