RPC 모드를 쓰면 호스트 프로그램이 에이전트를 자식 프로세스로 구동한다. 표준 입력으로 한 줄에 JSON 객체 하나를 보내고, 표준 출력에서 한 줄에 프레임 하나를 받는다. 다른 프로그램 안에 Horon을 넣고 싶고 프로세스를 직접 소유하며 스트리밍 출력·취소·세션 제어가 필요하지만 ACP를 말할 수 없을 때 쓰는 표면이다.

이 문서는 이 빌드가 구현한 계약과, 공개된 omp RPC 레퍼런스의 각 항목을 이 빌드가 어디까지 처리하는지를 행 단위로 밝힌다. Horon은 omp용으로 작성된 호스트가 Horon을 구동할 수 있도록 같은 와이어 프로토콜을 말한다. 처리할 수 없는 항목은 조용히 실패하지 않고 지원 표에 그렇게 적는다.

## 실행

```bash
horon-agent rpc                      # 서브커맨드 형태
horon-agent --mode rpc               # 플래그 형태, 같은 모드
horon-agent rpc --resume <session>   # 기존 세션에 붙기
```

두 형태는 같은 어댑터에 닿고, 호스트가 둘 다 넘기면 서브커맨드가 이긴다. `--session-dir`는 받되 무시한다. 세션은 Horon 홈 아래에 저장되므로 어댑터는 그것을 지킨 척하지 않고 경고를 남긴다.

표준 출력에는 프레임만 나간다. 진단은 로깅 서브시스템을 거쳐 표준 오류로 나가므로 호스트는 표준 출력을 걸러내지 않고 파싱한다. 표준 입력을 닫으면 프로세스가 끝나고, 진행 중인 턴이 있으면 그 턴을 마친 뒤 끝난다.

어댑터는 데몬이 없으면 띄우고, ACP 어댑터와 같은 방식으로 구독한 뒤 세션 기록을 읽는다. 모델 호출은 활성 `[providers.<name>]` 프로파일의 `type`이 고른 방식의 엔드포인트로 가므로 호스트를 띄우기 전에 그 프로파일이 준비돼 있어야 한다.

## 한 턴의 모양

최소 교환은 입력 두 줄과 승인 한 줄, 그 뒤 턴 프레임이다. `prompt` 응답은 턴이 돌기 *전에* 기록되므로, 그 응답을 기다리는 호스트가 긴 답변에서 교착되지 않는다.

```json
{"type":"ready","protocolVersion":1,"supportedProtocolVersions":[1],"maxFrameBytes":1048576,"maxReassembledFrameBytes":67108864,"supportsBashExcludeFromContext":true}
{"id":"p1","type":"prompt","message":"Reply with only the word ok"}
{"id":"p1","type":"response","command":"prompt","success":true}
```

텍스트만 있는 한 턴은 이 순서로 프레임을 쓴다. `agent_start`, `turn_start`, 사용자 `message_start`와 `message_end`, 어시스턴트 `message_start`, 그 `message_update`들, 어시스턴트 `message_end`, `turn_end`, `agent_end`, 그리고 `prompt_result`와 `session_settled`. 측정한 텍스트 한 턴은 `ready`부터 `session_settled`까지 19프레임이고, 도구 한 번을 쓰는 같은 측정이 58프레임이다. 호스트는 `agent_end` 앞에 끼어드는 `extension_ui_request`도 볼 수 있으므로 무시한다.

모든 프롬프트에 두 규칙이 적용된다.

- 턴이 완료됐든 중단됐든 실패했든 `prompt_result` 하나와 `session_settled` 하나가 정확히 프롬프트를 끝낸다. `prompt_result`에는 `agentInvoked`, `sessionSettled`와 함께 `status`(`completed`, `aborted`, `error`)가 실린다.
- 도구 실행은 어시스턴트 `message_end` *뒤에* 도착한다. 데몬은 응답이 닫히기 전에 도구 호출 인자를 스트리밍하지만, 호스트의 스텝 경계는 실행과 그 결과 메시지를 메시지 뒤에 둔다. 그래서 어댑터가 그것을 붙잡아 두었다가 내보낸다. 이 모드에서 순서를 바꾸는 곳은 여기 하나뿐이다.

프롬프트가 도는 동안에도 어댑터는 표준 입력을 계속 읽으므로 `steer`, `follow_up`, `abort_and_prompt`, `abort`, `get_state`, `negotiate_protocol`이 턴 중간에 동작한다. 나머지 명령은 대기열에 넣지 않고 `code: "busy"`로 거절한다. 대기시킨 `message`가 진행 중인 턴과 뒤섞이기 때문이다.

표준 입력은 전용 태스크가 읽는다. `select!`로 취소된 읽기는 이미 소비한 바이트를 잃어 최악의 순간에 프레임을 자르므로, 리더가 완성된 줄을 채널로 넘긴다.

## 호스트가 처리해야 하는 차이

- 버전 2를 협상하는 호스트는 버전 1로 응답을 받는다. 청크 없는 프레임을 받아들이도록 내려가야 한다. 이 빌드는 `rpc_chunk`를 절대 내보내지 않는다.
- 1메비바이트를 넘는 프레임은 대체된 프레임과 함께 `rpc_frame_error`로 보고되고 전달되지 않는다. 큰 도구 출력은 그래서 청크가 아니라 그 자신의 `tool_execution_end`로 호스트에 도달한다.
- `prompt_result`는 항상 기록되고 항상 `sessionSettled: true`를 실으므로, 호스트는 둘 다 기다리지 않고 `prompt_result`나 `session_settled` 중 하나로 턴을 끝낼 수 있다.
- 이 모드에서 호스트에 결정을 묻는 일은 없다. 승인과 질문은 데몬 쪽에서 해결되므로 `extension_ui_request`가 턴을 막지 않는다.

## 호스트 질문 기능 제안

상태는 #547 설계 제안이다. 위쪽의 동작은 현재 RPC v1 계약이다. 새 기능은 구조화된 질문과 선택지에 [하네스 API](/ko/reference/protocol/harness-api)의 타입이 정해진 `AskRequested`와 `ask_response` 계약을 재사용한다. 승인 결정은 기존 승인 채널에서 처리한다.

| 선택지 | 결과 |
| --- | --- |
| 기존 위젯 프레임에 대화상자 추가 | 질문 수명 주기가 호환용 프레임에 묶이고 기존 호스트가 예상하지 못한 프레임을 받을 수 있다. |
| 선택형 RPC v1 기능 추가 | 버전과 기존 프레임을 유지하면서 호스트가 제한된 질문을 표시할 수 있다. 이 방식을 선택한다. |
| 별도 UI 어댑터 추가 | 턴 처리와 취소 로직이 중복된다. |

호스트는 첫 프롬프트 전에 `capabilities: ["ask_v1"]`을 넣어 `negotiate_protocol`을 보낸다. 어댑터는 타입이 정해진 질문과 답변을 데몬에 연결할 수 있을 때만 `ask_v1`을 돌려준다. 필드가 없는 기존 협상 응답 형식은 유지한다. 첫 턴을 연결하기 전에 표준 입출력 연결에 합의한 기능을 확정하고 연결이 끝날 때까지 유지한다. 기능이 없으면 현재 데몬 동작을 따른다. 이전 어댑터가 필드를 생략하면 호스트는 지금처럼 RPC v1을 사용한다.

어댑터는 진행 중인 `AskRequested` 하나를 불투명한 `askId`와 타입이 정해진 `questions`를 담은 `ask_requested`로 바꾼다. 일반 명령 `id`, 동일한 `askId`와 타입이 정해진 `answers`로 `ask_response`를 받는다. 기존 `ask`의 구조와 크기 제한, RPC 프레임 상한과 연결당 대기 질문 묶음 하나의 제한을 적용한다. 제한 안에 표현할 수 없는 요청은 기존 데몬의 대체 처리로 마무리한다. 턴 실행 중에도 `abort`와 일치하는 `ask_response`를 포함해 표준 입력을 계속 읽는다. 잘못됐거나 오래된 ID에는 명령 ID와 연결된 오류를 응답하고 다른 대기 상태는 건드리지 않는다. 현재 연결에서 대기 중인 질문 묶음의 답변만 받는다. 데몬이 답변을 수락하면 성공을 알리고 해당 묶음을 닫는다. 같은 답변을 다시 보내면 이미 끝났다는 오류를 반환하고 두 번 반영하지 않는다.

기존 응답 기한은 데몬이 관리하고 어댑터는 기한을 다시 시작하지 않는다. 데몬 기한 초과, 호스트 표준 입력 종료, 중단 또는 턴 종료 시 대기 ID를 정리한다. 기능을 협상한 연결이 열려 있으면 ID와 이유를 담아 `ask_closed`를 보내고 호스트는 질문 화면을 닫는다. 기존 턴의 프롬프트 수신 확인, 종료 프레임 순서와 횟수를 유지한다. 호스트는 텍스트와 선택지를 데이터로 렌더링하고 어댑터는 프로세스 안에서 호스트 코드를 실행하지 않는다. ACP v1과 v2 어댑터는 독립적으로 유지한다.

### 구현 경계

1. `src/cli/rpc/`에서 협상과 프레임 검증을 확장한다. 새 프레임을 보내기 전에 기존 시작, 협상과 종료 프레임을 고정 입력으로 기록한다.
2. 타입이 정해진 질문과 답변을 변환하고 대기 ID 범위를 검사한다. 데몬이 처리를 끝내면 대기 ID도 정리한다. 프롬프트 구조와 기한 정책은 기존 `ask` 계약에 둔다.
3. 기능을 협상하는 호스트, 기존 호스트와 답하지 않는 호스트를 하위 프로세스로 검사한다. `cargo test --locked -p horon-agent --lib cli::`를 실행하고 GitHub Actions에서 해당 사례를 검사한다.

| 검증 동작 | 기대 결과 |
| --- | --- |
| `ask_v1`을 협상하고 턴 하나를 시작한 뒤 질문에 한 번 답한다 | 질문 프레임과 명령 ID가 연결된 성공 응답이 하나씩 나오고 `prompt_result`와 `session_settled`가 한 번씩 순서대로 나온다. |
| 오래된 ID와 중복 ID로 `ask_response`를 보낸다 | 오래된 답변은 대기 질문에 영향을 주지 않고 중복 답변은 두 번 반영되지 않는다. |
| 기능 필드가 없는 v1 호스트를 사용한다 | 시작과 턴 프레임이 기존 고정 입력 결과와 일치하고 새 질문 프레임은 나오지 않는다. |
| 답변 없이 기존 데몬 기한까지 기다린다 | 데몬의 기존 대체 처리가 한 번 실행된다. 호스트는 질문 닫힘과 종료 프레임을 각각 한 번 본다. |

시험용 프로바이더, 제어 가능한 데몬 시계와 JSONL 기록을 사용한다. 기존 데몬 기한 직전과 기한에 맞춰 시계를 움직인다. 처음에는 질문이 대기 중이고 다음에는 처리가 끝나는지 확인한다. RPC 하위 프로세스 검증에는 네트워크와 터미널 화면이 필요 없다.

## 선택형 A2UI v1.0 표면 기능(`a2ui_v1`)

표준 입출력 RPC 호스트는 첫 프롬프트 전에 A2UI v1.0 렌더링에 선택 참여할 수 있으며, 협상하지 않은 호스트의 동작은 바뀌지 않는다(`src/cli/rpc/command.rs`, `src/cli/rpc/frame.rs`).

| 프레임 / 필드 | 방향 | 역할 |
| --- | --- | --- |
| `negotiate_protocol` (`capabilities: ["a2ui_v1"]`, 선택 `a2ui`) | 호스트 -> 에이전트 | 연결 수명 동안 `a2ui_v1`과 선택적 렌더러 기능(`version`, `supportedCatalogIds`, `acceptsInlineCatalogs`)을 고정 |
| `a2ui_update` | 에이전트 -> 호스트 | 검증된 `agent_to_renderer` 봉투 한 건(`toolCallId`, `sequence`, `envelope`, 선택 `fallbackText`) 스트리밍 |
| `message_end` / `get_messages` (`type: "a2ui"` 항목) | 에이전트 -> 호스트 | 텍스트 블록과 함께 어시스턴트 A2UI 콘텐츠 항목(`envelopes`, 선택 `fallbackText`) 보존 |
| `a2ui_event` | 호스트 -> 에이전트 | 검증된 `action`, `callAgentFunction`, `error` `envelope`(선택 `dataModel` 포함)를 활성 세션으로 전달 |

- `a2ui_v1`을 생략한 연결에서는 `a2ui` 도구가 열리지 않고 `a2ui_update`가 나가지 않으며, `a2ui_event`는 오류 응답으로 거절된다.

### 일회성 `horon run` 플래그

`horon-agent run`은 `--a2ui`와 반복 가능한 `--a2ui-catalog <uri>`를 받는다(`src/cli/commands/a2ui_run.rs`). 일반 `horon run --a2ui`는 표준 출력에 읽기 쉬운 `[A2UI surface: ...]` 대체 카드를 찍고, `--json`은 JSON 응답에 `type: "a2ui"` 블록을 추가하며, `--ndjson`은 `type: "a2ui"` 스트림 프레임(`sequence`, `envelope`, `fallback_text`)을 내보낸다. `--a2ui` 없이 `horon run`을 실행하면 기본 도구 집합과 프롬프트 접두사가 바이트 단위로 그대로 유지된다.

## 검증

어댑터에는 데몬을 프로세스 안 소켓 쌍으로 스크립트하는 통합 시험이 있어, 데몬도 모델도 없이 실제 프로토콜 경로를 돌린다. 시작 핸드셰이크, 버전 협상, 알 수 없는 명령, JSON이 아닌 줄, `get_state`, 프롬프트 한 턴, 유휴 상태의 `abort`, 한도를 넘는 프레임, `set_todos` 저장, 모델 카탈로그 투영을 다룬다.

```bash
cargo test -p horon-agent --lib cli::rpc
python3 scripts/ci/check_docs_pairs.py
```

위 표의 증거 행은 각 명령을 처리하거나 각 프레임을 쓰는 파일과 줄을 밝히므로, 검토자는 아무것도 실행하지 않고 한 행을 확인할 수 있다.
