상태는 #571 설계 제안이다. 현재 프로필은 `extra_body`를 받는다. 제안은 해당 통신 방식과 요청 형식이 지원하는 모델을 대상으로 타입이 정해진 샘플링을 추가한다. [프로바이더 모델](/ko/reference/provider/model)

## 설계 결정

| 선택지 | 결과 |
| --- | --- |
| 공통 샘플링 사전 하나를 전송 | 일부 프로바이더나 모델이 거부할 필드도 보낸다. |
| 통신 방식과 모델마다 지원 목록 사용 | 요청 전에 검사하고 각 어댑터가 필드 이름을 정한다. 이 방식을 선택한다. |
| `extra_body`만 유지 | 프로바이더별 자유도는 유지되지만 공통 검증은 제공하지 않는다. |

## 입력과 전송 요청

모델 항목에는 지원되는 선택 설정을 명시할 수 있다. 타입 설정에 알 수 없는 키가 있으면 설정 오류로 처리한다. 값은 유한한 수 또는 지원하는 열거형 값이어야 하며 선택한 모델이 문서화한 범위 안에 있어야 한다. 키가 없으면 요청에도 필드를 넣지 않는다. 검토한 목록에 없는 모델에는 타입이 정해진 제어를 제공하지 않는다. 대체 후보도 요청 전에 각각 검사한다. 호환되지 않는 경로에는 요청을 보내지 않고 모델과 설정 이름을 알려 준다. 명시한 값을 조용히 빼거나 다른 샘플링 설정으로 재시도하지 않는다.

검토한 OpenAI 호환 Chat Completions 시험 모델의 `temperature`와 `top_p`부터 지원한다. 어댑터는 키를 한 번만 쓰고 값을 지정하지 않은 키는 생략한다. Top K, Min P, 존재 페널티, 반복 페널티와 장황함 제어는 v1 매핑에 넣지 않는다. Responses, Anthropic Messages와 Gemini generateContent도 v1 매핑에 포함하지 않는다. 각 후속 매핑에는 엔드포인트와 모델 근거, 모델별 범위와 조합 제한, 고정 요청 기록이 필요하다. 호환 프록시의 모델 지원은 별도로 확인한다. 기존 `extra_body`를 유지한다. 최종 `extra_body`에 같은 전송 키가 있으면 값이 같아도 거부하고 두 출처를 알린다. 타입 샘플링이 없는 기존 요청에는 평소대로 합친 `extra_body`를 적용한다.

## 구현 경계

1. `crates/config-types/src/named_provider.rs`에서 선택 필드의 타입을 정하고 잘못된 키와 타입, 충돌하는 설정을 거부한다.
2. `crates/base/src/provider/`와 `crates/provider-openai/src/`에서 선택한 경로의 지원 설정을 조회하고 전송 전에 검사한 뒤 검토한 Chat Completions 매핑으로 직렬화한다. 공통 인터페이스는 다른 통신 방식과 분리한다.
3. 엔드포인트와 모델 제약을 확인한 뒤 통신 방식별로 나누어 검토한다. 실제 자격 증명 없이 루프백 요청을 기록한다.

## 검증

`cargo test --locked -p horon-agent-config-types --lib`를 실행한다. GitHub Actions에서 `temperature = 0.4`만 지정한 시험 요청에 `temperature: 0.4`가 한 번 있고 `top_p`가 없는지 확인한다. 다음에는 `top_p = 0.8`만 지정해 반대 결과를 확인한다. `top_k`, 목록에 없는 모델, 시험 모델의 명시 범위 밖 값 또는 `extra_body`에서 같은 키를 고르면 요청을 보내기 전에 타입 검사 오류나 호환되지 않는 경로 안내를 기대한다. 타입 설정이 없는 요청은 기존 통신 시험 기록과 일치해야 한다.
