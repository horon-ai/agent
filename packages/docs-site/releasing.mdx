---
title: Packages and releases
description: How the repository publishes the CLI, the TypeScript SDK and the Python SDK, how versions are chosen, and how a tag becomes a published release.
---

The repository publishes three distribution sets from one release. The npm CLI
and the TypeScript SDK ship at the release tag's version; the Python SDK carries
its own version in `packages/sdk/python/pyproject.toml`. Sources live under
`packages/`.

## Layout

```text
packages/
  sdk/
    typescript/     @horon-ai/agent-sdk + six @horon-ai/agent-<os>-<arch> runtime packages
    python/         horon-agent-sdk (+ platform wheels)
  npm/
    horon/          @horon-ai/horon launcher + six @horon-ai/horon-<os>-<arch> packages
```

The TypeScript SDK ships at the release tag version: the publish workflow stamps
the tag into its checkout, and CI checks that the committed manifest and its six
runtime pins equal the root `Cargo.toml` version. The npm CLI keeps `0.0.0` in
git and receives the tag version in the published copy only.

## npm CLI

| Package | Contents |
| --- | --- |
| `@horon-ai/horon` | Launcher `bin/horon.js`; `bin` maps both `horon` and `hrn` to it. |
| `@horon-ai/horon-linux-x64` | `bin/horon-agent`, `bin/horon-tui` |
| `@horon-ai/horon-linux-arm64` | the same pair |
| `@horon-ai/horon-darwin-x64` | the same pair |
| `@horon-ai/horon-darwin-arm64` | the same pair |
| `@horon-ai/horon-win32-x64` | `.exe` pair |
| `@horon-ai/horon-win32-arm64` | `.exe` pair |

npm picks a platform package through `optionalDependencies`, so a global install
downloads only the one that matches the machine. Three properties keep the set
safe:

- Every platform pin is an exact version, never a range; a wrapper can never offer
  an install whose platform package does not exist at that version.
- No package declares an install script. `preinstall`, `install` and `postinstall`
  are absent from the generated manifests, and a platform package must not declare
  dependencies.
- Nothing is a Node library. The launcher reads `process.platform` and
  `process.arch`, resolves the matching package and starts `bin/horon-agent`
  through `spawnSync` with `stdio: "inherit"`. The child owns the terminal; the
  launcher ignores `SIGINT` and `SIGTERM` while it runs.

The launcher sets `HORON_AGENT_NO_AUTO_UPDATE=1` in the child's environment: the
package pins one release for both binaries, so an npm installation is updated with
npm. A missing platform package is a reinstall, not a broken install; the launcher
prints one `horon:` line and exits 1.

## TypeScript SDK

`@horon-ai/agent-sdk` plus one `@horon-ai/agent-<os>-<arch>` package per supported
platform, published at the same tag version behind the `SDK_NPM_PUBLISH` gate
(separate from the CLI's `NPM_PUBLISH`). It has
its own workflow file because npm trusts a top-level workflow file name for the
Trusted Publisher registration.

## Python SDK

`horon-agent-sdk` publishes a pure wheel, an sdist, and six platform wheels: Linux
and macOS and Windows, each for x86_64 and arm64. Platform wheels carry the
runtime; the pure wheel and sdist do not, so `launch()` falls back to
`horon-agent` on `PATH`. Its version comes from
`packages/sdk/python/pyproject.toml`, and a publish run names the release tag
whose runtime binaries are bundled into the platform wheels.

## Versions

`[package].version` in the root `Cargo.toml` names the release line (MAJOR.MINOR)
and the lowest patch on that line; tags number the later patches, so no commit
bumps the version and a release can never start another release. When CI for a
push to `main` succeeds, `release-tag.yml` asks `scripts/release/next_version.py`
for the next tag, creates it on that exact commit and calls `release.yml`. A tag
pushed by hand triggers `release.yml` directly and goes through the same checks.
Setting the repository variable `RELEASE_AUTO` to `false` stops automatic
tagging, and a manual run of `release-tag.yml` only reports the tag it would
create.

Every release starts as a draft. Its notes are rendered from the commit subjects
since the previous tag, grouped by conventional-commit prefix and ended with the
compare link. `Finalize release` publishes the draft only when every platform
asset exists; a partial set stays a draft.

The published release carries the agent and `horon-tui` archives for Linux, macOS
and Windows, the agent archive for FreeBSD, `SHA256SUMS`, and a
`linux/amd64` + `linux/arm64` container image at `ghcr.io/horon-ai/agent` tagged
`<version>`, `<MAJOR.MINOR>` and `latest`. Browse the published versions on
[GitHub Releases](https://github.com/horon-ai/agent/releases).

## Release flow

1. Work lands on `dev`; `main` is what ships.
2. A release merges `dev` into `main` with a merge commit. When CI for that push
   succeeds, the tag is created on that exact commit and `release.yml` starts (see
   [Versions](#versions)).
3. `release.yml` builds on GitHub-hosted runners: Linux x86_64 inside the
   manylinux2014 container for a glibc 2.17 baseline, Linux aarch64 on
   `ubuntu-24.04-arm`, macOS on `macos-latest` and `macos-15-intel`, Windows x64
   on `windows-latest` and Windows ARM64 on `windows-11-arm`, and FreeBSD x86_64
   inside a FreeBSD 15.1 VM. A failed platform leaves the release in draft.
4. The container image is published from the finished, verified Linux assets.
5. Package publishing is gated behind `NPM_PUBLISH` and runs only from the tag
   workflow, never from a pull request. The Python SDK is dispatched separately
   with its own version.
