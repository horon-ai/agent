# 기억 위키

언어: [English](MEMORY.md) | **한국어**

기억 위키는 기억을 담는 사용자별 저장 엔진이다. 페이지 하나가 마크다운 파일 하나이고 그것이 정본이며, SQLite 인덱스는 언제든 그 파일들에서 다시 만들 수 있는 파생 데이터다. 임베딩을 저장하지 않고 네트워크 왕복도 필요 없다. 이 문서는 저장소 배치, 페이지 형식, 인덱스 스키마, 검색 신호, 삭제와 재생성 규칙, 한국어 평가, 현재 한계를 다룬다. 이 위키는 `memory` 도구와 프롬프트 주입 경로의 저장소다. 모든 `memory` action이 이 위키를 읽고 쓰며, 위키 이전의 JSON 파일은 한 번만 마이그레이션 원본으로 읽는다.

## 배치

모든 파일은 `$HORON_HOME/memory`( `HORON_HOME`이 없으면 `~/.horon/memory`) 아래에 있다.

```text
memory/
  wiki/
    preferences/<id>.md
    people/<id>.md          # kind person
    entities/<id>.md
    facts/<id>.md
    procedures/<id>.md
    corrections/<id>.md
    lessons/<id>.md
    custom/<id>.md
    events/<YYYY>/<MM>/<id>.md
    preferences/<project>/<id>.md   # 프로젝트 범위 페이지
  index.sqlite
  index.sqlite-wal
  index.sqlite-shm
```

`wiki/`의 부모가 저장소 루트이고, 그 부모가 `$HORON_HOME`이다. 그래서 사용자 볼륨에는 그 사용자의 기억만 들어가고, 컨테이너는 그 사용자의 볼륨만 마운트한다. 위키 디렉터리는 `0700`, 페이지 파일은 `0600`으로 만든다.

### 페이지 id와 파일 이름

id와 파일 이름은 같지 않다. 소문자 ASCII 글자, 숫자, `.`, `_`, `-`로 시작하고 같은 문자로만 이루어진 평문 id만 그대로 파일 이름이 된다. `goal:6f96…`, `skill:deploy checklist`, 대문자나 한글이 섞인 id는 `~` 뒤에 UTF-8 바이트를 소문자 16진수로 적은 이름으로 저장한다. `~`는 평문 알파벳에 없으므로 변환이 뒤집을 수 있고 중복이 없다. 평문 이름은 소문자만 쓰므로 대소문자를 구분하지 않는 파일 시스템(macOS, Windows)에서 두 id가 한 파일로 겹치지 않는다. 빈 id, 256바이트를 넘는 id, `.`으로 시작하는 id(`.`과 `..`이 파일 이름이 되지 않게), 경로 구분자, 제어 문자는 검증에서 거부한다. 읽을 때도 정규 형식이 아닌 파일 이름은 거부하므로, 손으로 복사한 별칭이 두 파일을 한 페이지로 묶지 않는다.

## 페이지 형식

페이지는 frontmatter 블록 하나와 기억 본문으로 이루어진다.

```text
---
schema: 1
id: "mem_1732000000000_42"
title: "민열님은 아침 회의를 선호"
kind: "preference"
category: "preference"
project: "horon-agent"
tags: ["schedule", "meeting"]
entities: ["민열", "SURI"]
links: [{kind: relates_to, dst: "mem_2_b", weight: 0.5}]
valid_from: "2026-11-01"
valid_to: null
confidence: 0.8
source: "conversation/2026-11-21"
created_at: "2026-11-21T10:00:00Z"
updated_at: "2026-11-21T10:00:00Z"
access_count: 3
trust: "medium"
strength: 2
active: true
superseded_by: null
reinforcements: [{session: "session-1", message_index: 4, timestamp: "2026-11-21T10:00:30Z"}]
---
본문 텍스트
```

이 문법은 YAML이 아니라 직접 쓴 엄격한 하위 집합이다. 위에 있는 필드만 받는다. 모르는 필드는 거부하므로, 오타 하나가 값을 조용히 지우지 않는다. 규칙은 다음과 같다.

- 파일은 `---` 줄로 시작하고, 블록은 다음 `---` 줄에서 끝난다. 그 뒤는 전부 본문이며 그대로 둔다. 본문 안의 `---` 줄은 그냥 본문이다.
- 필드는 한 줄에 `key: value` 하나다. 키는 소문자 ASCII 식별자이고 중복될 수 없다. 필드는 최대 64개, 줄은 최대 8 KiB다.
- 문자열은 큰따옴표로 감싼다. `"`, `\`, 줄바꿈, 캐리지 리턴, 탭과 그 밖의 제어 문자는 `\"`, `\\`, `\n`, `\r`, `\t`, `\uXXXX`로 이스케이프한다. 모르는 이스케이프, 그대로 들어간 제어 문자, 닫히지 않은 문자열, 잘못 적은 리터럴, 값 뒤의 군더더기는 모두 거부한다.
- 숫자는 정수 또는 소수이고, `true`, `false`, `null`이 나머지 스칼라다.
- 목록은 `[a, b]`, 맵 목록은 `[{k: v}, {k: v}]`다. `links`와 `reinforcements`가 맵 형식을 쓴다.

쓰는 쪽의 출력은 정규 형식이다. 페이지를 쓰고, 다시 읽고, 다시 쓰면 같은 바이트가 나온다. 그래서 파일을 손으로 고치고 diff로 확인해도 안전하다.

### 필드

| 필드 | 형식 | 뜻 |
| --- | --- | --- |
| `schema` | 정수 | 페이지 스키마. 이 빌드는 `1`을 쓰고 다른 값은 거부한다. 없으면 1로 본다. |
| `id` | 문자열 | 페이지 id. 손으로 쓴 페이지에서 없으면 파일 이름에서 id를 얻는다. |
| `title` | 문자열 | 필수. 사람이 읽는 이름이며 최대 400자, NUL 금지. |
| `kind` | 문자열 | 필수. `preference`, `person`, `event`, `fact`, `procedure`, `correction`, `lesson`, `entity`, `custom`. 디렉터리와 순위 권위를 정한다. |
| `category` | 문자열 | 페이지가 나타내는 기억 범주다. `fact`, `preference`, `entity`, `correction`, `lesson` 또는 소문자 사용자 범주. 없으면 종류의 기본 범주를 쓴다. 그래서 손으로 쓴 페이지에도 범주가 있다. |
| `project` | 문자열 또는 null | 페이지가 속한 프로젝트 키. 안전한 경로 한 조각이어야 한다. 소문자, 숫자, `_`, `-`, 최대 64자. `null`은 사용자 전역이다. |
| `tags` | 문자열 목록 | 자유 태그. 최대 64개, 각 최대 64자. |
| `entities` | 문자열 목록 | 사람, 조직, 프로젝트 이름. 최대 128개, 각 최대 128자. |
| `links` | 맵 목록 | `{kind, dst, weight?}`. kind는 `relates_to`, `supersedes`, `contradicts`, `derived_from`이다. `relates_to`는 `0..=1` 가중치가 필수이고 나머지는 가중치가 없다. 자기 자신이나 중복 링크는 거부한다. |
| `valid_from`, `valid_to` | 날짜 또는 null | `YYYY-MM-DD` 유효 기간. 없는 쪽은 열려 있다. |
| `confidence` | 숫자 | `0..=1`. |
| `source` | 문자열 또는 null | 페이지가 나온 곳. |
| `created_at`, `updated_at` | 타임스탬프 | UTC RFC 3339. 손으로 쓴 페이지에 없으면 파일 수정 시각을 쓴다. |
| `access_count`, `strength` | 정수 | 조회 횟수와 통합 강도. |
| `trust` | 문자열 | `high`, `medium`, `low`. |
| `active` | 불리언 | 현재 유효한 페이지인지. `active: true`인 페이지는 `superseded_by`를 가질 수 없다. |
| `superseded_by` | 문자열 또는 null | 이 페이지를 대체한 페이지 id. |
| `reinforcements` | 맵 목록 | `{session, message_index, timestamp}` 흔적. 최대 256개. |

기존 `MemoryEntry`가 가진 값은 임베딩만 빼고 모두 이 형식으로 살아남는다. 임베딩은 파생 데이터이므로 일부러 저장하지 않는다. `MemoryPage::from_entry`와 `MemoryPage::to_entry`가 `access_count`, `trust`, `strength`, `active`, `superseded_by`, `reinforcements`, `confidence`를 포함해 두 표현을 서로 옮긴다. 범주는 별도 필드에 두므로 사용자 범주 이름도 왕복한다. 페이지 링크는 `EdgeKind`로 옮겨지고, `relates_to`는 가중치를 유지하며 태그·클러스터 엣지는 페이지 링크가 아니다.

종류별 권위는 높은 순서대로 `preference`, `person`, `correction`이 5, `procedure`, `lesson`, `entity`가 4, `fact`, `custom`이 3, `event`가 1이다. 이 가중치가 같은 관련도의 선호를 일정보다 위에 두게 한다.

## 인덱스 스키마

`index.sqlite`는 파생 데이터다. `PRAGMA user_version`이 스키마 버전이고 지금은 1이다. 데이터베이스는 WAL 모드로 열고 `secure_delete=ON`, `trusted_schema=OFF`, 5초 busy timeout을 쓴다.

| 객체 | 내용 |
| --- | --- |
| `pages` | 페이지 한 줄: id, 경로, kind, category, project, title, body, 태그·엔티티 JSON, `updated_ms`, `created_ms`, `active`, 유효 기간, source. |
| `tags` | `(page_id, tag)`. 태그 필터에 쓴다. |
| `links` | `(src_id, dst_id, kind, weight)`. |
| `entities` | `(page_id, name, name_norm)`. `name_norm`은 비교에 쓰는 소문자 영숫자 형태다. |
| `versions` | `(page_id, rev, body, created_at)`. `rev`는 1부터 시작한다. |
| `files` | `(path, page_id, mtime_ns, size)`. 재조정 때 바뀌지 않은 파일을 건너뛰는 데 쓴다. 스탬프가 나노초 정밀도라, 마지막 색인 커밋과 같은 밀리초에 쓰인 변경도 건너뛰지 않는다. |
| `pages_fts` | title, body, tags, entities 위의 `fts5(unicode61 remove_diacritics 2)`. |
| `pages_bigram` | title, body 위의 `fts5(trigram)`. 세 글자 이상 부분 문자열을 찾는다. |
| `pages_grams` | title, body의 겹치는 bigram 확장 위의 `fts5(unicode61)`. 띄어 쓰지 않은 한국어·CJK 질의를 찾는다. |
| `meta` | 키/값 기록. |

세 전문 색인 테이블 모두 FTS5 `secure-delete` 옵션을 켜므로, 삭제한 용어는 빈 페이지에 남지 않고 덮어쓴다.

## 검색

`MemoryWiki::search`는 텍스트 스트림 네 개와 링크 스트림 하나로 후보를 모은 뒤, 상수 60의 reciprocal-rank fusion으로 합친다.

| 스트림 | 찾는 것 | 가중치 |
| --- | --- | --- |
| `pages_fts` | 토큰 색인을 통한 질의 단어 | 1.0 |
| `pages_bigram` | 세 글자 이상 부분 문자열 | 1.0 |
| `pages_grams` | CJK bigram. `아침회의선호`가 `아침 … 회의를 선호`에 닿는다 | 1.0 |
| entities | 질의가 frontmatter 엔티티 이름을 포함할 때 그 페이지 | 1.0 |
| links | 텍스트 상위 세 건의 1홉 이웃 | 0.8 |
| recency | 후보를 마지막 쓰기, 첫 쓰기 순으로 | 1.0 |
| authority | 후보를 종류 권위 순으로 | 1.5 |

최근성과 권위는 후보 집합만 정렬한다. 텍스트나 링크가 찾은 것을 다시 정렬할 뿐이므로, 최근이라는 이유만으로 무관한 페이지가 나타나지 않는다. 같은 스트림 안에서 근거가 같으면 같은 순위를 준다(조밀 순위). 그래서 본문이 같은 두 페이지는 id 알파벳 순서가 아니라 최근성과 권위로 갈린다. 최종 순서는 점수, 마지막 쓰기, id 순이고 모두 명시적이므로 같은 인덱스는 같은 질의에 늘 같은 답을 한다.

각 결과는 스트림별 순위를 함께 갖는다. 이상해 보이는 순서를 추측하지 않고 설명할 수 있게 하려는 것이다.

질의는 SQLite에 닿기 전에 정리한다. 모든 용어는 FTS5 구문 인용으로 감싸고 내부 따옴표는 두 번 적으므로, 사용자 글자가 FTS5 문법을 주입할 수 없다. 글자나 숫자가 없는 질의는 빈 결과를 낸다. 세 글자 미만의 CJK 부분 문자열은 trigram 테이블이 아니라 bigram 스트림이 맡는다. 필터는 종류, 프로젝트, 태그, 유효 날짜(`YYYY-MM-DD`)로 좁히고, 같은 필터를 링크 이웃에도 적용하므로 이웃이 필터를 빠져나가지 못한다.

## 쓰기, 버전, 삭제

`MemoryWiki::write_page`는 파일을 먼저 쓴다. 같은 디렉터리에 임시 파일을 만들고 fsync한 뒤 소유자 전용 권한을 주고 rename하고 부모 디렉터리를 fsync한다. 그다음 `BEGIN IMMEDIATE` 인덱스 트랜잭션 하나로 페이지, 전문 색인 세 줄, 태그, 엔티티, 링크, 새 `versions` 줄을 기록한다. 그 사이에 프로세스가 죽으면 파일이 정본이므로 다음 열기가 색인에 넣는다. 종류나 프로젝트가 바뀌면 페이지를 옮기고, 새 페이지를 색인한 뒤 이전 파일을 지운다.

쓸 때마다 새 본문을 담은 버전 줄이 하나 늘어난다. 버전은 인덱스 데이터다. 페이지를 지우면 함께 지우고, 전체 재생성은 마크다운이 유일한 정본이므로 현재 본문만 다시 만든다.

`MemoryWiki::delete_page`는 마크다운 파일을 먼저 지우고, 한 트랜잭션으로 페이지의 인덱스 줄을 모두 지운 뒤, 같은 id를 주장하는 중복 파일을 훑어 지우고, `PRAGMA secure_delete=ON`, FTS5 `optimize`, `VACUUM`, `wal_checkpoint(TRUNCATE)`를 차례로 실행한다. 색인은 id당 페이지 하나만 가질 수 있으므로, 손으로 복사한 파일을 치우지 않으면 그 파일이 살아남는다. 순서가 계약이다. 파일을 지운 뒤 죽으면 유령 줄만 남고 다음 열기가 정리하며, 반대 순서면 재생성이 페이지를 되살린다.

그 보장의 한계도 적어 둔다. SQLite는 자기가 할당한 영역을 0으로 덮고 빈 페이지를 회수하지만, 파일 시스템 저널, SSD 웨어 레벨링, 백업 스냅샷은 그 통제 밖이다. 최종 수단은 볼륨 계층의 키 폐기이고, 그것은 이 저장소가 아니라 볼륨 수명 주기의 일이다.

## 재생성

`MemoryWiki::open`은 열 때마다 인덱스를 파일과 재조정한다. 수정 시각(나노초 정밀도)과 크기가 기록된 스탬프와 같은 파일은 건너뛰고, 바뀐 파일은 다시 읽어 색인하며, 파일이 사라진 줄은 지운다. 삭제를 확정하는 것이 이 정리다. 인덱스가 없거나, 스키마 버전이 다르거나, 손상된 데이터베이스면 처음부터 다시 만든다. 손상은 감지해서 파일과 `-wal`/`-shm` 곁파일을 지운 뒤 다시 만든다. 잠긴 인덱스는 초기화하지 않는다. 다른 작성자가 쓰는 파일을 지우면 그 작업이 사라지기 때문이다.

깨진 페이지 하나가 열기를 실패시키지 않고, 그 파일을 지우지도 않는다. 마지막 재조정 보고서에 경로와 이유를 남기고, 그 페이지의 이전 색인 줄은 그대로 두며, 나머지 위키는 색인한다. 같은 페이지 id를 주장하는 파일이 둘이면 정렬된 경로에서 앞선 파일을 색인하고 뒤엣것을 중복으로 보고한다.

`MemoryWiki::reindex`는 파생 테이블을 모두 비우고 모든 파일을 다시 읽는다. 페이지를 경로 순서로 읽고 융합의 동점 처리 규칙이 명시적이므로, 같은 파일은 재생성 전후에 같은 결과를 낸다. 테스트가 `index.sqlite`를 지우고 결과 목록을 비교해 이것을 확인한다.

심볼릭 링크는 따라가지 않는다. 위키 안의 심볼릭 링크는 페이지가 아니고, 인덱스에 기록된 경로가 위키 루트를 벗어나면(`..`, 절대 경로, Windows 접두사) 거부하며, 페이지를 읽을 때 그 경로가 심볼릭 링크면 거부한다.

## 한국어 평가

저장소에는 합성 한국어 비서 기억과, 한국어 사용자가 실제로 치는 키워드·엔티티·무공백 질의로 이루어진 작은 고정 평가 세트가 있다(`crates/base/src/memory/store/korean_eval.json`). 공개 벤치마크가 아니며 공개 수치를 인용하지 않는다.

- 페이지: 14개(선호, 사람 둘, 일정 둘, 사실, 절차, 교훈, 정정, 엔티티).
- 질의: 15개. 무공백 형태(`아침회의선호`, `테스트격리`, `빌드잠금`), 조사가 붙은 형태(`디자인 리뷰 일정`, `배포는 언제 하나`), 엔티티만 있는 형태(`김서연`, `박준호`)를 포함한다.
- 방법: 고정 세트로 저장소를 만든 뒤 질의마다 검색하고, 기대 페이지 id 중 하나가 상위 k에 있으면 그 질의를 맞힌 것으로 센다.
- 2026-11-23 측정 결과: recall@1 15/15, recall@3 15/15, recall@5 15/15. 테스트가 이 수치를 고정하므로, 질의 하나를 잃는 순위 변경은 기준을 조용히 낮추지 않고 실패한다.

## `memory` 도구의 저장소

이 위키는 더 이상 별도 엔진이 아니다. `MemoryManager`가 백엔드를 통해 이 위키를 읽고 쓰며, 그 백엔드는 관리자의 어휘인 스코프별 기억 그래프를 유지한다(`crates/base/src/memory/backend.rs`).

- **읽기**는 해당 스코프의 페이지에서 그래프를 만든다. **쓰기**는 바뀐 그래프를 페이지와 비교해 반영한다. 필드가 바뀐 페이지는 다시 쓰고, 그래프에서 빠진 페이지는 지우며, 바뀌지 않은 페이지는 그대로 둔다. 도구 action 하나가 그래프 변경 하나와 저장소 쓰기 하나다. 태그 여러 개짜리 `tag`도 쓰기 한 번이다.
- **저장소마다 쓰기 주체 하나.** 모든 변경은 읽기-변경-쓰기 전체를 `memory/.write.lock` 배타 잠금으로 감싼다. 그래서 한 프로세스의 두 핸들이나 두 프로세스가 같은 그래프를 읽고 서로 덮어쓸 수 없다. 그 아래에서 인덱스의 `BEGIN IMMEDIATE` 트랜잭션이 쓰기를 직렬화한다.
- **오래된 읽기 없음.** 인덱스에는 모든 쓰기 트랜잭션 안에서 증가하는 리비전 카운터가 `meta` 테이블에 있다. 프로세스 전역 그래프 캐시는 (저장소, 스코프, 리비전)으로 키를 잡는다. 그래서 어느 핸들·스레드·프로세스의 쓰기든 다음 읽기를 다시 계산하게 만들고, 쓰기 이전 상태로 답하지 않는다. 통합 요약도 같은 방식으로 키를 잡으므로 forget이나 update가 주입되는 요약을 다시 만든다.
- **임베딩은 저장하지 않는다.** 파생 데이터이기 때문이다. `crates/base/src/memory/retrieval.rs`의 dense·hybrid 헬퍼는 호출자가 같은 호출에서 넘긴 벡터로 계속 점수를 낼 수 있지만, 오늘 그것을 요구하는 운영 경로는 없다. recall은 Jev가 맡고, 로컬 검색은 `search`가 늘 해 온 부분 문자열 매칭이다. `backfill_embeddings`는 디스크에 채울 것이 없으므로 0을 보고한다. JSON 형식으로 저장된 기억의 벡터는 마이그레이션이 건드리지 않는 원본 JSON 파일에만 남는다.

### 프로젝트 키

프로젝트 기억은 그 디렉터리에서 유도한 키 아래에 산다. 정규 경로의 SHA-256 16진 앞자리 32자다. 한 디렉터리의 두 표기(심링크, `/var`와 `/private/var`, 끝의 `.`)는 한 키로 모이고, 이름이 같은 다른 디렉터리는 충돌하지 않으며, 사용자 프로젝트 안에는 아무것도 쓰지 않는다. 키는 `crates/base/src/memory/project_key.rs`에 있다.

위키 이전 키는 호출자의 `PathBuf`에 대한 `DefaultHasher` 값이었다. 그 값은 되돌릴 수도 없고 안정된 디스크 계약도 아니므로 마이그레이션 원본 이름으로만 남는다. 프로젝트를 열 때 옛 해시(예전과 같은 알고리즘·같은 표기)와 새 키를 모두 계산하고, 그 해시의 옛 파일을 처음 볼 때 가져온다.

### JSON에서 마이그레이션

`horon-agent memory migrate [--dry-run]`은 찾은 모든 위키 이전 파일 — `memory/global.json`과 모든 `memory/projects/<hash>.json` — 을 위키로 가져온다. 관리자도 첫 사용 때 전역 파일과 현재 프로젝트 파일을 가져오므로 업그레이드에 별도 명령이 필요 없다. 이 명령은 모든 프로젝트를 한 번에 옮기고 결과를 보고하려고 있다.

- **멱등.** 각 페이지는 원본이 가진 id로 한 번씩 쓰인다. 중간에 멈춘 실행은 쓴 것을 남기고 다음 실행이 나머지를 마저 쓴다. 원본 파일은 경로·크기·SHA-256·기억·엣지 수, 실행 시각, 도구 버전과 함께 `memory/migration.json`에 기록되고, 바이트가 바뀌지 않은 파일은 파싱 없이 건너뛴다. 두 번째 실행은 페이지를 하나도 쓰지 않고 `wiki/` 아래 바이트도 바꾸지 않는다.
- **원본은 절대 수정·삭제하지 않는다.** JSON 파일도 `.bak`도 아니다. 이것이 마이그레이션을 안전하게 만들고 바이트 단위 비교를 가능하게 한다.
- **실패는 반쪽 마이그레이션을 남기지 않는다.** 저장할 수 없는 페이지는 보고되고 같은 파일의 나머지는 계속 가져온다. 중간에 중단된 실행은 쓴 페이지를 남기고, 인덱스는 그것에서 다시 만들 수 있으며, 다음 실행이 마저 완료한다. 어느 경우든 원본은 그대로다.
- **이 빌드가 읽을 수 없는 파일은 추측하지 않고 거절한다.** `graph_version`이 2가 아니거나 JSON이 파싱되지 않으면 파일 이름과 버전을 담은 메시지로 실패하고 아무것도 쓰지 않는다. 예전 로더의 버전 함정(다른 버전 그래프가 평면 저장소 파싱 오류로 떨어지던 것)은 이제 명시적 거절 하나다.
- **기존 위키 사본이 더 새로우면 그것이 이긴다.** 낡은 JSON을 다시 가져올 때 그 기억은 덮어쓰지 않고 건너뛴 것으로 센다.
- **해시 이름 파일에서 가져온 페이지는 `legacy-<hash>` 아래에서 시작한다.** 해시는 경로로 되돌릴 수 없어 명령이 프로젝트 키 아래에 둘 수 없다. 그 프로젝트를 처음 열 때 페이지가 안정된 키로 옮겨진다. 페이지 id는 그대로이므로 복사가 아니라 파일을 다시 쓰는 이동이다.

**되돌리기.** `memory/wiki`와 `memory/index.sqlite`(`-wal`·`-shm` 포함)를 지운다. JSON 원본이 그대로 있으므로 이전 릴리스가 예전과 똑같이 읽는다. `memory/` 밖의 상태는 관여하지 않는다.

**가져오지 않는 것:** 임베딩(파생이며 다시 만들 수 있다), 그리고 저장소 수준 병합이 바꿀 만한 것. 기억 필드나 엣지 중 버려지는 것은 없다.

## 기억 항목 내보내기

`horon-agent memory export <output> [--scope global|project|all]`는 저장된 기억 항목(`MemoryEntry`)을 `<output>`으로 내보낸다. 내보낸 항목 필드에 포함된 인식 가능한 자격 증명은 마스킹 처리하며, 파일은 `O_NOFOLLOW`와 소유자 전용 권한(`0o600`)으로 기록한다.

## 볼륨 내보내기, 가져오기, 삭제

호스팅 사용자는 루트가 `HORON_HOME`인 볼륨 하나를 소유하고, 그 안 `memory/` 아래의 기억 위키가 운영자가 백업하고 옮기고 파괴하는 대상이다. `horon volume` 명령이 그 일을 한다. 컨트롤 플레인이 tar를 전달하고 Fly API 호출을 소유하며, 에이전트는 그 파일을 만들고 읽는다.

| 명령 | 하는 일 |
| --- | --- |
| `horon volume export <path> [--key-id <id>] [--key-env <var> \| --key-file <file>]` | `wiki/`, `metadata.jsonl`, `manifest.json`을 담은 tar를 `<path>`에 쓴다. 기록자 잠금 아래 한 리비전만 읽으며, 키 지정 시 `aes-256-gcm`으로 인증 암호화한다 |
| `horon volume import <path> [--key-env <var> \| --key-file <file>]` | **새 빈** 저장소에 풀고, manifest 대조(및 `aes-256-gcm` 복호화)를 마친 뒤 마크다운에서 `index.sqlite`를 다시 만든다 |
| `horon volume quiesce` | 인덱스 로그를 체크포인트하고, 페이지 파일과 인덱스를 fsync하며, 이후 쓰기를 막는다 |
| `horon volume resume` | 쓰기 펜스를 푼다 |
| `horon volume key create`/`show`/`revoke` | 사용자 데이터 키 레코드를 만들고, 보여 주고, 폐기하며, 폐기할 때 준비된 키 자재를 지운다 |
| `horon volume delete-user <user_id>` | 삭제 단계 기계를 돌린다. 쓰기를 막고, 키를 폐기하고, 저장소를 지우고, 모든 스냅숏을 지우고, Machine과 볼륨을 지운 뒤, 중앙 행을 `deleted`로 표시한다 |
| `horon volume deletion-status` | 저장된 작업과 그 단계를 보여 준다 |

**tar.** `wiki/`는 페이지 파일(`none`) 또는 `HME1` `aes-256-gcm` 암호문 항목을 담는다. `metadata.jsonl`은 페이지마다 JSON 객체 하나를 담고, 식별자, 종류, 카테고리, 프로젝트, 태그, 엔티티, 날짜, 횟수, 신뢰도, 본문 크기를 적는다. 본문은 적지 않는다. 본문은 이미 페이지 파일에 있고, 중복하면 카탈로그나 지원 티켓 첨부가 실어 나를 수 있는 산출물에 기억 본문이 들어가기 때문이다. `manifest.json`은 형식 버전, 저장소 리비전, 암호화 필드(`none` 또는 `aes-256-gcm`), 선택적 `key_id`, 파일마다 `{path, bytes, sha256}` 행을 담는다. 키도 토큰도 서명 URL도 들어가지 않는다.

**가져오기는 증명할 수 없는 것을 거부한다.** manifest에 없는 페이지 파일, 크기나 SHA-256이 다른 파일, 메타데이터 줄과 다른 페이지 id로 해독되는 파일은 어떤 파일도 쓰기 전에 거부한다. 절대 경로이거나 `..`로 벗어나거나 심볼릭 링크, 하드 링크, 장치, fifo인 항목도 거부한다. 압축을 푼 항목 수와 총 크기는 상한이 있다. 인덱스는 마크다운에서 다시 만들므로 원본 볼륨의 파생 데이터는 신뢰하지 않고, 가져온 페이지 수가 manifest와 같아야 한다.

**스냅숏 전 quiesce.** 볼륨 스냅숏은 기껏해야 크래시 일관성이며, 플랫폼은 파일시스템 동결을 문서로 보장하지 않는다. `quiesce`는 기록자 잠금을 잡고, SQLite write-ahead 로그를 `TRUNCATE`로 체크포인트하며, 페이지 파일과 인덱스를 fsync하고, `memory/.write-fence.json`을 쓴다. 이 파일이 있으면 `resume`까지 모든 저장소 쓰기가 거부된다. 데이터 손실 구간은 명시적이다. quiesce 없이 찍은 스냅숏은 승인된 마지막 몇 초의 쓰기를 놓칠 수 있고 첫 열기에서 전체 재색인이 필요할 수 있다.

**사용자 삭제.** `<HORON_HOME>/volume-state/deletion-job.json`의 작업 파일이 단계가 끝날 때마다 기록되고 저장소 밖에 있다. 저장소를 지우는 단계가 기록을 잃지 않게 하려는 것이다. 순서가 계약이다. 쓰기가 멈추고, 키가 폐기되고(빠져나간 사본이 파괴되기 전에 읽을 수 없게), 스냅숏이 지워지고, 볼륨이 파괴되고, `deleted`가 마지막에 기록된다. 실패한 단계는 이유와 함께 남고 재시도할 수 있으며, `deleted`는 모든 단계가 끝난 뒤에만 보고된다.

**키 계약과 아카이브 암호화.** 볼륨은 키 레코드(`key_id`, 알고리즘 id, `created_at`, `revoked_at`)를 가지며 키 자재는 두지 않는다. 자재는 컨트롤 플레인의 키 서비스가 소유하고, 에이전트는 공급자 인터페이스로 요청한다. 폐기된 키는 볼륨 열기와 해당 볼륨의 암호화 내보내기를 거부한다. `--key-env`·`--key-file`(또는 `export_with_key`·`import_with_key`)을 주면 `metadata.jsonl`과 모든 `wiki/` 항목을 항목별 96비트 난수와 형식 버전·리비전·`key_id`·경로 AAD가 묶인 `AES-256-GCM`으로 봉인한다. `--key-file`은 소유자 전용 일반 파일(`0600` 또는 `0400`, 심볼릭 링크·그룹/타인 읽기 허용 파일 거부)이어야 한다. 키 없는 `import`는 암호문을 마크다운으로 설치하지 않고 거부하며, 디스크 위 상시 페이지는 Fly 볼륨 저장 시 암호화를 그대로 따른다.

**중앙 메타데이터에는 기억 본문이 없다.** 클라이언트는 초안 `horon-ai/server#28` 계약에 대해 식별자, 상태, 타임스탬프, 키 id, 스냅숏 id, 객체 키만 보낸다. 요청 타입에는 본문, 텍스트, 제목, 태그, 경로 필드가 없고, 테스트가 모든 요청을 루프백 서버로 보내 표시자 본문이 요청 바이트 어디에도 나오지 않음을 확인한다. 계약은 초안이다. 확정된 엔드포인트도 스키마도 없고, 모든 중앙 호출은 트레이트 하나 뒤에 있어 컨트롤 플레인이 전송 방식을 바꿀 수 있다.

## 한계

- 임베딩과 벡터 검색이 없다. 검색은 어휘, 엔티티, 링크 기반이므로 단어도 엔티티도 링크도 공유하지 않는 바꿔 말하기는 찾지 못한다.
- `pages_bigram`은 세 글자 이상 부분 문자열을 맡는다. 더 짧은 CJK 부분 문자열은 bigram 확장과 토큰에 기대므로, 두 음절 질의는 bigram이나 단어가 맞을 때만 찾는다.
- 버전은 인덱스 데이터다. `index.sqlite`를 지우면 기록은 사라지고 현재 본문만 남는다.
- 사용자 볼륨 안에 git 기록을 두지 않는다. 삭제 요청이 저장소에 옛 버전을 남기면 안 되기 때문이다.
- 물리 삭제는 SQLite가 할당한 범위까지만 보장한다. 자세한 내용은 삭제 절에 있다.
- 내보내기·가져오기·볼륨 전체 삭제는 마크다운에서 인덱스를 다시 만든다. 원본 볼륨의 버전 기록은 버전이 인덱스 데이터이므로 사라진다.
- 마이그레이션은 버전 2 그래프만 읽는다. 경로를 정규화할 수 없는 디렉터리(지금 존재하지 않는 디렉터리)는 절대 경로로 대체되며, 이때만 한 디렉터리의 두 표기가 서로 다른 키를 만들 수 있다.
